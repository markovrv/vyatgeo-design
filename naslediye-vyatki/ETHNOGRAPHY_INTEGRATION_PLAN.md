# План интеграции модуля «Этнография» с WordPress API

Раздел: `src/views/EthnographyView.vue` + `src/views/EthnographyItemView.vue`.
Источник данных: плагин `api/artifact-finder` (CPT `finding`), REST на `https://testsite.vyatgeo.ru/wp-json/`.

<!-- impeccable:product-schema 1 -->

## 1. Текущее состояние

### 1.1 API (бэкенд) — готово
- CPT `finding`, 767 записей, кастомный эндпоинт `GET findings/v1/findings/` с пагинацией и фильтрами по `finding_material`, `finding_origin`, `finding_creation_time`, `finding_type`, `search`.
- Таксономия `finding_type` (10 терминов) — у каждого термина загружено изображение через медиабиблиотеку, REST-поле `finding_type-image` отдаёт готовую ссылку (`GET /wp/v2/finding_type` / `/wp/v2/finding_type/{id}`).
- 651 из 767 находок уже классифицированы по типу (см. `api/classification_result.json`); 116 — без типа, требуют ручной разметки музеем через wp-admin.

### 1.2 Vue-фронтенд — полностью статичный прототип
- `EthnographyView.vue` — захардкоженный массив из 12 демо-объектов, собственная инлайн-карточка (не переиспользует `CatalogCard.vue`).
- Фильтры — «По народу» (people) и «По типу» (type), оба через `FilterBar` (пилюли).
- `EthnographyItemView.vue` — единственный жёстко зашитый объект («Дымковская игрушка»); маршрут `/ethnography/:slug` существует в роутере, но компонент параметр **не читает вообще**.
- Во всём проекте нет ни одного `fetch`/`axios` — see `PRODUCT_VUE.md`: «No live backend; all data is static prototype content».

## 2. Расхождения данных — нужны решения до реализации

### 2.1 Фильтр «По народу» (этнос) — в API такого поля нет
Текущие демо-значения (Русские/Татары/Удмурты/Марийцы/Коми) не соответствуют ничему в бэкенде. Ближайшая таксономия `finding_origin` — это место находки/сборов или ФИО дарителя (например «Кировская область», «Сборы в Кирово-Чепецком районе», «Дар Бердинских В.А.»), а **не этнос**.

Варианты:
- **(a) Убрать фильтр «по народу»** при переходе на реальные данные — рекомендую, источника правды нет.
- (b) Завести на бэкенде новую таксономию `finding_ethnos` и вручную разметить 767 находок — объём работы сопоставим с тем, что уже сделано для `finding_type` (отдельный проект).
- (c) Оставить как декоративный, ничего не фильтрующий — не рекомендую, вводит в заблуждение.

**План ниже написан в расчёте на (a).** Если нужен вариант (b) — это отдельный этап, аналогичный уже проделанному для типов.

### 2.2 Идентификатор объекта в URL — slug или id
Кастомный REST не отдаёт `post_name` (slug), только `id`. Варианты:
- **(a) Роут `/ethnography/:id`** (числовой) — бэкенд трогать не нужно, id уникален всегда. Рекомендую для первого этапа.
- (b) Добавить `'slug' => $post->post_name` в ответ `findings/v1/findings/` (небольшой PHP-патч) и оставить человекочитаемые URL — красивее, но требует ещё одного релиза плагина, и slug не стабилен при переименовании заголовка находки.

Переход с (a) на (b) позже не потребует менять остальную архитектуру — только роут и то, что подставляется в `RouterLink :to`.

### 2.3 Черновая классификация типа — 58% меток не подтверждены человеком
В `classification_result.json` у 58% находок стоит `needs_review: true` (rule-based и LLM разошлись, финальная метка — лучшая догадка). В WP это уже записано как единственный термин `finding_type`, без пометки «черновой/подтверждён». Фронтенд не может отличить проверенные метки от непроверенных без доп. поля на бэкенде (например булево мета `finding_type_verified`).

**Предлагаю на этом этапе показывать тип как есть**, без визуальной пометки — данные лучше, чем их отсутствие. Если для музея важно визуально различать черновые метки — отдельная будущая доработка (мета-поле + бейдж «требует проверки» на карточке).

### 2.4 Проверить фото типов на подмену
При выгрузке заметил похожие имена файлов у разных терминов: «Торговля» → `Promysly-1.jpg`, «Сельско-хозяйственные инструменты» → `SKh_instrumenty-1.jpg`, «Плотницко-столярные инструменты» → `SKh_instrumenty.jpg`. Может быть случайным совпадением при выборе из медиабиблиотеки — но стоит визуально сверить в wp-admin, что каждой из 10 плиток соответствует правильная картинка, **до** того как они попадут на сайт.

## 3. Архитектура интеграции

### 3.1 Единая константа адреса API

`index.html`, глобальная переменная перед подключением `src/main.js`:

```html
<script>
  window.__API_BASE_URL__ = 'https://testsite.vyatgeo.ru/wp-json/';
</script>
```

Такой же паттерн уже использовался в старом `history/spa` (`window.apiUrl`) — сохраняем консистентность с уже знакомым подходом в этом же проекте. Главное преимущество: адрес меняется прямо в собранном `dist/index.html` на сервере, **без пересборки** Vue-бандла — то есть ровно то, что вы просили («будет меняться, для всех модулей сразу»).

Единая точка чтения — новый файл `src/config/api.js`:

```js
export const API_BASE_URL = window.__API_BASE_URL__ || 'https://testsite.vyatgeo.ru/wp-json/'
```

Все 7 модулей импортируют константу отсюда — единообразно на будущее, когда остальные разделы (Attraction/Geopoints/History) тоже перейдут на реальные данные.

### 3.2 Слой доступа к данным

Новый composable `src/composables/useFindings.js`:
- `fetchFindings()` → `GET {API_BASE_URL}findings/v1/findings/?per_page=1000` — все находки одним запросом (767 записей — не тяжелее, чем уже сделано в `attraction/v1/objects`, который тоже грузит всё разом через `posts_per_page: -1`).
- `fetchFindingTypes()` → `GET {API_BASE_URL}wp/v2/finding_type?per_page=100` — 10 терминов с `finding_type-image`, для плиток фильтра.

Загрузка — один раз при входе на страницу, дальше фильтрация полностью на клиенте (сохраняем уже существующий `computed(() => items.filter(...))`-паттерн из `EthnographyView.vue` — меняется только источник `items`, не сама логика фильтрации).

## 4. Каталог: фильтр по типу как фото-плитки

Заменить `<FilterBar label="По типу" .../>` (текстовые пилюли) на плитки по образцу `.module-card` с главной страницы (`IndexView.vue`) — фото + подпись, как разделы каталога (см. секцию `#modules`).

Новый компонент `src/components/TypeFilterTiles.vue`:
- Пропсы: `types` (массив `{id, name, image, count}`), `active`, `@select`.
- Плитка «Все» — без картинки или с общей заглавной картинкой раздела (`ethnography.jpg`).
- Вёрстка/стили — переиспользование `.module-card`/`.module-bg`/`.module-overlay`/`.module-text` из `IndexView.vue` (стоит вынести в общий CSS-класс вместо копирования, раз шаблон уже есть в двух местах).
- Данные — `fetchFindingTypes()`.

## 5. Карточка каталога — расширенный набор данных

Сейчас `CatalogCard.vue` показывает: картинку, произвольные теги, заголовок, одну строку meta, описание. Предлагаемый набор полей для карточки находки (максимум из доступного в API):

| Элемент карточки | Источник данных |
|---|---|
| Фон карточки | `thumbnail` |
| Бейдж номера по каталогу | `cat_id` (например «Э-724») — как в PHP-шаблоне (`.catalog-badge`) |
| Бейдж типа (с иконкой) | `type[0]` + `finding_type-image` соответствующего термина |
| Заголовок | `title` |
| Строка meta 1 | `materials.join(', ')` |
| Строка meta 2 | `creation_time.join(', ')` |
| Строка meta 3 (если непусто) | `origin.join(', ')` |
| Краткое описание | `functionality`, обрезанное до ~120 симв.; fallback — `content` |

Текущий пропс-контракт `CatalogCard.vue` (`img/tags/title/meta/desc`) под это не рассчитан — нужна либо специализированная обёртка `FindingCard.vue` (рекомендую: `EthnographyView.vue` и так уже рисует свою инлайн-карточку, не через общий `CatalogCard`, так что это просто замена содержимого существующей инлайн-разметки, без риска для остальных 6 модулей), либо расширение самого `CatalogCard.vue` под несколько строк meta (тогда нужно свериться, что это не сломает Victory/Nature/Archeology/Architecture, которые уже используют его as-is).

## 6. Страница объекта — синхронизация с шаблоном PHP-плагина

Порядок и состав полей должны совпадать с тем, что рендерит сам плагин на сервере (`get_finding_detailed_layout` / `get_finding_fields_html`, `api/artifact-finder/artifact-finder.php`) — чтобы «бумажная» версия в wp-admin/сервере и Vue-версия на сайте показывали одну и ту же картину находки, не расходясь составом полей.

| Порядок в PHP-шаблоне | Поле API | Показывать в Vue, если |
|---|---|---|
| Галерея (карусель) | `additional_images`, fallback `thumbnail` | всегда |
| Номер по описи | `cat_id` | `cat_id` непуст |
| Понятие (описание) | `content` | всегда |
| Тип | `type` (+ иконка `finding_type-image`) | `type` непуст |
| Функционал | `functionality` | непуст |
| Особенности | `features` | непуст |
| Материал | `materials.join(', ')` | непуст |
| Размеры (ш×д×в) см | `dimensions` | непуст |
| Происхождение | `origin.join(', ')` | непуст |
| Время поступления | `receipt_time.join(', ')` | непуст |
| Время создания | `creation_time.join(', ')` | непуст |

`EthnographyItemView.vue` сейчас использует произвольную структуру секций («Место и время бытования», «Этнос и материалы» со статами) — под реальные данные её нужно заменить на список полей выше (условно рендерящихся только при наличии данных, как и в PHP: `if ($value && trim(strip_tags($value)))`).
