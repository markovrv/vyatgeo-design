# Проект «Наследие Вятки» (Vue-версия)

Историко-культурное наследие Кировской области — сайт к 90-летию региона (1936–2026). Эта директория (`naslediye-vyatki/`) — рабочая Vue 3 + Vite реализация; статический HTML-прототип в корне репозитория (`../index.html`, `../*.html`, `project/*.dc.html`) сохранён только для референса дизайна и не разрабатывается дальше.

На сегодня с реальным API **на фронтенде** интегрированы все 6 каталожных модулей — **Архитектура** (`attraction`), **Этнография** (`artifact-finder`/findings), **Города** (`history` + таксономия `city`: лента времени по городам с пагинацией/поиском, карточки и hero городов, реальная Яндекс.Карта с пинами-городами, координаты и мини-карта в админке термина), **Археология** (`archeology` + таксономии `archeology_era` и `archeology_type`: каталог/карта с фильтрацией по эпохе и типу, реальная Яндекс.Карта с пинами-памятниками), **Природа** (`oopt-kirov`/CPT `oopt`, 17 записей, таксономии `oopt_district`/`oopt_profile`/`oopt_species`) и **Лица Победы** (`geroi-vyatki`/CPT `hero`, 215-216 записей — Герои Советского Союза, уроженцы/связанные с Вятским краем; единственная таксономия `hero_status`). Плюс седьмой раздел — **«О проекте»** (`/about`, обычная WP-страница). Мок-данных в навигируемых разделах SPA больше нет. Блок «Вятский край: семь веков истории» на главной (`IndexView.vue`) тоже не статика — вехи подтягиваются из реальных событий Кирова (`useHistoryMilestones`, см. ниже).

Природа и Лица Победы — самые свежие из интегрированных, построены по паттерну Археологии/Архитектуры (composable + `CatalogLayout` + карта с кластеризацией + страница объекта с adjacent/nearby/комментариями), с двумя частными решениями, которых не было у более ранних модулей:

- **У «Лиц Победы» реальные данные покрывают только Героев Советского Союза ВОВ** — прежний мок `VictoryFacesView.vue` с пятью историческими периодами (Золотая Орда, Первая мировая и т.д.) полностью удалён вместе с `VictoryPersonView.vue`, а не оставлен частично как раньше планировалось (см. историю правок `api/prompt-victory-nature-integration.md`) — текст hero-секции переписан так, чтобы не заявлять охват периодов, которых нет в данных.
- **Фильтры обоих модулей (район/профиль/охраняемые виды у Природы, эпоха/тип у Археологии) собраны в сворачиваемую панель «Фильтры»**, а не показываются всегда открытыми рядами над картой — см. паттерн `controls-group`/`.controls-group--floating` ниже.

Подробности контракта бэкенда — `api/docs/geroi-vyatki.md`, `api/docs/oopt-kirov.md`, `api/prompt-geroi-oopt-plugins.md` (исходное ТЗ на плагины), `api/prompt-victory-nature-integration.md` (ТЗ на интеграцию фронтенда этих двух модулей).

Помимо этих 6 каталожных модулей + «О проекте», на фронтенде подключены сквозные функции WordPress, не привязанные к одному разделу:

- **Страницы (Pages)** — `usePage.js` + общий `PageView.vue` (hero с заголовком страницы и фото/фолбэком + HTML-контент + комментарии). «О проекте» (`/about`) — не отдельный компонент, а обычная WP-страница (slug `about`) на этом же шаблоне; создаётся автоматически при активации темы, если её ещё нет (`nv_spa_ensure_about_page()`). Произвольные страницы — по маршруту `/page/:slug`.
- **Записи (Posts)** — раздел «Новости» (`/news`, `/news/:id`), `usePosts.js`/`usePost.js`, серверная пагинация и поиск.
- **Комментарии** — `useComments.js` + `CommentsSection.vue`: чтение одобренных и гостевая отправка. Подключены на страницах объектов всех 6 каталожных модулей и на Pages/Posts.
- **Меню** — SPA не хардкодит навигацию насовсем: `useMenu.js` тянет пункты из WP-меню (`spa_primary` — шапка, `spa_footer` — футер) через кастомный REST `nv/v1/menu/{location}`, с фолбэком на прежний захардкоженный список, пока редактор не назначил меню в WP. Оба меню создаются автоматически при активации темы с этим же списком в качестве стартового содержимого.

Подробности паттернов и частых грабель — см. раздел «Паттерны сквозных фич» ниже.

## Тема WordPress (SPA Shell)

Тема `wp-theme/naslediye-vyatki-theme/` — минимальная оболочка для headless-режима: отключает стандартный вывод WP и отдаёт собранный Vue-билд (`dist/index.html`) на все фронтовые URL. `wp-admin`, `wp-login.php`, `/wp-json/` тема не трогает.

### Customizer API

Конфигурация SPA (API-адрес, ключ Яндекс.Карт, радиус поиска) вынесена в Customizer (**Внешний вид → Настроить → Конфигурация приложения**) и не требует правки `dist/index.html`:

| Настройка | `theme_mod` | Переменная |
|---|---|---|
| API Base URL | `nv_api_base_url` | `window.__API_BASE_URL__` |
| Yandex Maps API Key | `nv_yandex_maps_api_key` | `window.__YANDEX_MAPS_API_KEY__` |
| Радиус «Объекты рядом» (км) | `nv_attraction_nearby_radius_km` | `window.__ATTRACTION_NEARBY_RADIUS_KM__` |

Принцип работы: `nv_spa_render_app()` читает `dist/index.html`, вставляет `<script>`-блок со значениями из `get_theme_mod()` перед `</head>` и отдаёт результат. Customizer-скрипт выполняется после дефолтного `<script>` из `index.html`, переопределяя `window.__*__`. `transport: 'refresh'` — страница перезагружается при сохранении.

### Docker (локальное тестирование темы)

```bash
cd wp-theme
docker compose up -d       # WordPress + MariaDB на порту 8080
docker compose down         # остановка
docker compose down -v      # остановка + удаление БД
```

- Фронтенд/SPA: http://localhost:8080
- Админка: http://localhost:8080/wp-admin/
- Тема НЕ примонтирована как volume — правки PHP-файлов и билда нужно копировать в контейнер вручную через `docker cp` (см. ниже). ZIP-загрузка темы через WP-админку не работает из-за прав на volume с dist/.
- `.htaccess` с mod_rewrite генерируется автоматически скриптом `ensure-htaccess.sh` (без него статика `/assets/*` не доходит до WordPress)

Для копирования PHP-файлов темы:
```bash
docker cp "wp-theme/naslediye-vyatki-theme/functions.php" wp-theme-wordpress-1:/var/www/html/wp-content/themes/naslediye-vyatki-theme/
docker cp "wp-theme/naslediye-vyatki-theme/menu-api.php" wp-theme-wordpress-1:/var/www/html/wp-content/themes/naslediye-vyatki-theme/
docker cp "wp-theme/naslediye-vyatki-theme/admin/import.php" wp-theme-wordpress-1:/var/www/html/wp-content/themes/naslediye-vyatki-theme/admin/
```

Для копирования билда:
```bash
rm -rf dist wp-theme/naslediye-vyatki-theme/dist
npm run build:theme
MSYS_NO_PATHCONV=1 docker exec wp-theme-wordpress-1 rm -rf /var/www/html/wp-content/themes/naslediye-vyatki-theme/dist
MSYS_NO_PATHCONV=1 docker cp "wp-theme/naslediye-vyatki-theme/dist" wp-theme-wordpress-1:/var/www/html/wp-content/themes/naslediye-vyatki-theme/dist
```

Два грабли в этой последовательности, оба поймались вживую:

- **`dist/` не самоочищается между сборками в этом окружении** — повторный `npm run build`/`build:theme` без предварительного `rm -rf dist` (и `wp-theme/.../dist`) добавляет новые content-hash файлы, не удаляя чанки от предыдущей сборки. В контейнер вместе с новым кодом уезжает и старый — какой из двух реально отдаётся, зависит от того, на какой хэш ссылается свежесобранный `index.html`, и это не всегда очевидно на глаз (баг может казаться неисправленным, хотя правка в коде верна). Перед каждым `build:theme`, который будет копироваться в Docker/на сервер, — сначала `rm -rf dist wp-theme/naslediye-vyatki-theme/dist`.
- **Git Bash на Windows подменяет POSIX-пути в аргументах команд** (`/var/www/html/...` превращается в путь относительно установки Git) — из-за этого `docker exec ... rm -rf /var/www/html/...` может тихо ничего не удалить (путь не резолвится, `rm -rf` завершается без ошибки на несуществующем пути), и следующий `docker cp` скопирует новую сборку поверх старой, не подчистив её — те же старые чанки, что и в предыдущем пункте, только уже как отдельная причина. Решение — `MSYS_NO_PATHCONV=1` перед `docker exec`/`docker cp`, как в примере выше.

После деплоя стоит свериться, что хэш реально отданного `index-*.js` совпадает с тем, что лежит в контейнере на диске:
```bash
curl -s http://localhost:8080/ | grep -o 'assets/index-[A-Za-z0-9_]*\.js'
MSYS_NO_PATHCONV=1 docker exec wp-theme-wordpress-1 sh -c "ls /var/www/html/wp-content/themes/naslediye-vyatki-theme/dist/assets/ | grep '^index-'"
```

Для копирования файлов плагинов:
```bash
docker cp "api/archeology/." wp-theme-wordpress-1:/var/www/html/wp-content/plugins/archeology/
```

Для пересоздания контейнера после правок в `docker-compose.yml`:
```bash
docker compose up -d --force-recreate wordpress
```

## Паттерны модулей с реальным API

Ниже — то, что устоялось во всех 6 интегрированных модулях (Архитектура, Этнография, Города, Археология, Природа, Лица Победы) и стоит повторять один в один в любой будущей доработке, а не изобретать заново.

### Composables (`src/composables/use*.js`)

- Список: `useXxxs()` → `{ items, loading, error, fetchXxxs }`. Один объект: `useXxx()` → `{ item, loading, error, fetchXxx(id) }`. Никогда не бросают наружу исключения — ошибка складывается в `error.value`, компонент сам решает, что показать.
- Состояние каталога — реактивный **module-level singleton** (`export const xxxCatalogState = reactive({...})`), а не `ref` внутри компонента: так фильтр/страница/scrollY переживают переход на страницу объекта и возврат назад. Восстановление скролла — через `onBeforeRouteLeave` (сохранить) + `onMounted` (`nextTick` + `requestAnimationFrame` дважды, чтобы дождаться реального рендера, затем `window.scrollTo`).
- `SITE_URL` (домен без `wp-json/`) экспортируется рядом с `API_BASE_URL` — нужен и для относительных URL в HTML-контенте (`../../` → абсолютный), и для ссылок в `wp-admin`.
- Заголовки WP иногда приходят с буквальными HTML entity-кодами (`&#8212;`) — раскрывать вручную через скрытый `<textarea>` (`decodeEntities`), сервер это не делает.
- Если у сущности нет своих таксономий (как у `attraction`) — не выдумывать фильтры на фронте, которых нет в данных.
- **`GET /wp/v2/{cpt}` ограничен `per_page=100` — WP REST отклоняет большее значение `400 rest_invalid_param`, а не молча обрезает список.** Если каталогу нужны таксономии сразу в bulk-ответе (см. следующий пункт про Природу/Героев) и в модуле больше 100 записей (у `hero` — 215/216), `fetchXxxs()` обязан постранично догрузить остальные страницы и объединить результат (первый запрос без `page`, читать `X-WP-TotalPages` из заголовка ответа, затем `Promise.all` по оставшимся страницам) — см. `useHeroes.js`. Без этого каталог не покажет вообще ни одной записи: `res.ok` будет `false`, композабл уйдёт в `error.value`, и симптом на экране неотличим от «API не отвечает».
- **Если каталогу для клиентской фильтрации по таксономии нужны сами термины, а не только координаты/фото/аннотация** — не использовать лёгкий кастомный bulk-эндпоинт (`{module}/v1/objects`), он таксономию не отдаёт по контракту (см. §«REST-паттерны на бэкенде» ниже). Вместо него — штатный `GET /wp/v2/{cpt}?per_page=100&_embed=1`, при датасете в пределах пары сотен записей это не накладнее и сразу даёт `_embedded['wp:term']` для фильтрации на клиенте (см. `useOoptSites()`/`useHeroes()`). Лёгкий bulk-эндпоинт при этом никуда не девается — он просто не тот инструмент для каталога с фильтрами по таксономии, бэкенд трогать не нужно.

### Каталог (`CatalogLayout.vue`)

- Слоты: `#heading`, `#description`, `#filters`, `#map`, `#grid`, `#pagination`. Общий для всех модулей компонент, его вёрстку под конкретный модуль не форкать — расширять через слоты.
- Переключатель «Карта/Каталог» + поиск — единый узнаваемый паттерн сайта: `FilterBar` (пунктирные пилюли-чипы, 1.5px dashed, ochre-заливка на активном) + `.search-box` (сплошная рамка 1.5px, радиус `var(--radius)`, ochre-обводка по фокусу, `min-height: 44px`) — см. `AttractionControls.vue`. Не изобретать новый стиль тумблера/инпута под очередной модуль.
- **Если у модуля больше одной таксономии-фильтра** (район/профиль/охраняемые виды у Природы, эпоха/тип у Археологии) — не показывать их всегда открытыми рядами над картой; собирать в сворачиваемую панель «Фильтры» рядом с переключателем/поиском (см. `NatureControls.vue`/`ArcheologyControls.vue`): кнопка-тоглер со счётчиком активных фильтров и шевроном — **в той же строке**, что переключатель карта/каталог и поиск (справа, после `.search-box`, который растягивается на всё доступное место и естественно прижимает тоглер к правому краю), а не отдельной строкой над ней. Сама раскрывающаяся панель (`MultiSelectFilter` на каждую таксономию, `display:grid; repeat(auto-fit, minmax(200px,1fr))`) рендерится не в самой строке контролов, а в `#map`-слоте `CatalogLayout` сразу под ней — обе обёрнуты в общий `.controls-group`/`.controls-group--floating`-контейнер (тот же приём floating/inline, что и раньше был только у самой строки контролов): в режиме карты вся группа (строка + раскрытая панель) плавает над картой единым блоком, в режиме каталога — обычная колонка в потоке над сеткой. Если оборачивать только строку контролов, а панель оставить в отдельной секции `CatalogLayout` (`#filters`-слот) — в floating-режиме панель не будет иметь точки привязки под строкой и не сможет визуально с ней объединиться. Счётчик активных фильтров в кнопке — сумма длин выбранных массивов (`state.era.length + state.type.length` и т.п.), кнопка «Сбросить» рядом с тоглером обнуляет все массивы разом.
- **Не хардкодить опции фильтра, если это реальная WP-таксономия** (в отличие от фиксированных внутренних ключей вроде `era`/`type` у Археологии, которые приходят из собственного bulk-контракта `archeology/v1/objects`, а не из WP) — WP генерирует `slug` термина из кириллического названия **без транслитерации**: реальный slug у «Историческая» — не `istoricheskaya`, а процент-кодированная строка `%d0%b8%d1%81%d1%82...`. Захардкоженный список вида `{ value: 'gidrologicheskiy', label: 'Гидрологический' }` не совпадёт ни с одной записью и фильтр молча всегда будет отдавать 0 результатов — без единой ошибки в консоли, поймать на глаз почти невозможно (так были найдены и исправлены баги в `hero_status` и `oopt_profile`). Строить опции фильтра из уже загруженного каталога (`buildTermOptions()` в `NatureView.vue`) или через `useTaxonomyOptions(taxonomy)` из `useFindings.js`.
- Если карте нужен весь набор данных сразу (кластеризация не работает постранично) — грузить всю коллекцию одним запросом, а каталожный вид фильтровать/пагинировать **на клиенте** поверх этого же массива, а не городить серверную пагинацию только ради второго режима просмотра.
- **Исключение** — если у вида нет карты и датасет большой (лента времени Кирова — 666+ записей на один город): грузить постранично с сервера (`page`/`per_page`, по 10 штук) и подгружать по мере прокрутки через `IntersectionObserver` на пустом sentinel-элементе в конце списка, а не разом. Век/поиск в этом случае — **тоже серверные параметры** (`meta_query`/`s` в `WP_Query`), не клиентский фильтр поверх уже загруженного куска: иначе первая страница при активном фильтре могла бы прийти пустой, хотя подходящие записи есть дальше. Кэш уже загруженных страниц и текущий фильтр — module-level singleton (как и остальное состояние каталога), при возврате со страницы объекта показывает то же самое, а не сбрасывается к первой странице (см. `historyEventsCache`/`historyTimelineState` в `useHistory.js`).
- Локальный «Загрузка…» при смене фильтра/поиска должен закрывать **только список результатов**, а не всю страницу через общий верхний `v-if="loading"` — если под этот же флаг попадает ещё и герой/шапка/панель управления, при каждой смене фильтра страница схлопывается до одной строки текста, браузер обрезает scrollY по новой (маленькой) высоте документа, и после перерисовки страница остаётся наверху, а не там, где был пользователь. Нужны раздельные `loading`-флаги: один — «страница/город ещё не загружены вообще» (гейтит всю страницу), другой — «текущий список перезагружается» (гейтит только список). Массив элементов при этом не обнулять сразу на время запроса — старые результаты остаются на экране до прихода новых, тогда смена фильтра/поиска ощущается мгновенной, без схлопывания и «прыжка» прокрутки (см. `CityTimelineView.vue`).
- Bulk-эндпоинты часто отдают только маленькую WP-миниатюру (обычно 150×150) — той же самой, что используется для пинов карты. Для карточек шире ~300px она размывается. Решение — батч-запросом взять готовый размер получше: `GET /wp/v2/media?include=id1,id2,...&_fields=id,media_details` (именно так, без вложенных путей вида `media_details.sizes.large` — WP тихо режет такие вложенные `_fields` и отдаёт пустой объект вместо ошибки), один запрос на видимую страницу каталога, не на каждую карточку отдельно (см. `useAttractionThumbnails`).
  - **Цепочка фолбэка обязана доходить до оригинала**: `medium_large` → `large` → `medium` → `full`, и только если во всём объекте `sizes` вообще пусто — оставлять миниатюру из массового ответа. WP генерирует размер, только если оригинал больше его порога, поэтому у части объектов (на живых данных Архитектуры — 62 из 423, то есть ~15%) `medium_large` (768px) и `large` (1024px) отсутствуют одновременно, потому что оригинал изначально мельче. Если остановиться на `medium_large → large → null`, эти ~15% молча откатываются на 150×150 и размытость вылезает точечно, уже после релиза — воспроизвести на глаз на паре тестовых объектов почти невозможно, нужно было проверить весь набор через `/wp/v2/media` вручную, чтобы поймать. Не сокращать цепочку ради лаконичности кода.
  - **Справочник `id вложения → URL` из батч-апгрейда не должен жить в локальном `ref` внутри composable**, если на страницу можно вернуться после перехода на объект: composable вызывается заново при каждом монтировании компонента, `ref` создаётся пустым, а вотчер на список элементов повторно не срабатывает (сам список элементов часто берётся из уже готового module-level кэша и не меняется) — миниатюры молча откатываются на 150×150 при возврате. Справочник должен быть module-level `ref` (переживает переход туда-обратно) и дополнительно зеркалироваться в `sessionStorage` (переживает и перезагрузку вкладки) — при записи в `sessionStorage` не дублировать в каждой записи домен, которого и так знает `SITE_URL`: хранить путь без домена, разворачивать в абсолютный URL при чтении (см. `historyThumbnailsCache`/`toRelativeUrl`/`toAbsoluteUrl` в `useHistory.js`).

### Карта (`AttractionMap.vue`, `vue-yandex-maps`)

- `initYmaps()` перед монтированием дочерних компонентов карты — у библиотеки бывает гонка при обычном автоинициализирующем монтировании.
- Кластеризация — `yandex-map-clusterer` с кастомной иконкой; кастомные маркеры — через `yandex-map-marker` со слотом.
- Кастомные контролы (`yandex-map-control-button`): обёртка библиотеки добавляет свой фиксированный паддинг (~8px с каждой стороны) поверх заданного размера вложенного контента — если нужен точный итоговый размер кнопки (как у соседних штатных контролов), считать размер вложенного `<span>` в обратную сторону (итог минус паддинг с двух сторон), а не выставлять размер самого контрола. Подсказка — своя всплывающая карточка в стиле проекта, не полагаться на нативный `title` (плохо стилизуется).
- Полноэкранный просмотр фото — всегда через переиспользуемый `ImageLightbox.vue` (зум, яркость/контраст, клавиатура, счётчик уже реализованы там). Не дублировать эту логику внутри очередного попапа/карусели — просто открывать `ImageLightbox` по клику на фото.
  - **В `ImageLightbox.vue` зум сделан явным пересчётом ширины/высоты картинки в пикселях** (`computeFitSize` по `naturalWidth/Height` + размеру контейнера), а не `transform: scale()` с `object-fit: contain`: `object-fit` не меняет layout-размер элемента, поэтому в момент пересечения `scale > 1` картинка «прыгала» на свой натуральный (часто в разы больший) пиксельный размер. Центрирование содержимого сделано через `margin: auto` на самой картинке, а не `align-items/justify-content: center` на скролл-контейнере — иначе переполнение в сторону начала осей (верх/лево) недоступно прокруткой ни в одном браузере, это общая особенность flexbox-центрирования с `overflow: auto`. Зум «от точки» (курсор/центр экрана остаётся на месте) реализован прямым пересчётом `scrollLeft/scrollTop`, а не CSS `transform-origin`. Не возвращаться к `transform: scale` + `transform-origin` для зума — оба бага уже были пойманы и исправлены один раз.
- Панель управления (переключатель + поиск) на карте — floating-плашка поверх карты в режиме карты, и та же панель обычной строкой над сеткой в режиме каталога (один компонент, два визуальных состояния через модификатор класса). Отступы от краёв — одинаковые в обоих режимах, чтобы при переключении режима элементы не «прыгали» по горизонтали. Паттерн общий на все модули с картой (не только Архитектура) — см. также `HistoricCitiesView.vue`.
- **Лёгкий вариант карты** (без кластеризации/исторических слоёв/попапа — просто пины с фото и переходом по клику, как у городов на `HistoricCitiesView.vue`/`HistoryCitiesMap.vue`) не нужно собирать из полной версии `AttractionMap.vue` вырезанием лишнего — отдельный маленький компонент с тем же набором примитивов (`YandexMap`, `YandexMapMarker`, `initYmaps`, `fitToPoints` по bounds точек) читается проще, чем `AttractionMap.vue` с закомментированными кусками.
- **Координаты для сущностей без своего REST-эндпоинта записи** (таксономия, а не CPT — например, «Город») хранятся term meta-полем `"lat, lng"` строкой, тем же форматом, что и `attraction_coord`/`geopoints_coord` у CPT. Мини-карта для ввода координат в редакторе термина — тот же классический Yandex Maps JS API v2.1 (`ymaps.Map`/`ymaps.GeoObject`, НЕ `vue-yandex-maps`/ymaps3, который используется только во Vue-фронте) и тот же скрипт-паттерн, что и в админке Архитектуры/Гео-точек (`api/attraction/js/adminMap.js`, `api/geopoints/js/adminMap.js`) — клик по карте и ручной ввод в текстовое поле синхронно обновляют друг друга. Копия скрипта на таксономию — `api/history/js/adminCityMap.js`, подключается только на экранах добавления/редактирования термина (enqueue внутри колбэков `{tax}_add_form_fields`/`{tax}_edit_form_fields`), а не глобально.

### Страница объекта (`{Module}ItemView.vue` / `{Module}ObjectView.vue`)

Общая структура сверху вниз: breadcrumb → intro (заголовок + место) → summary/content → галерея → навигация «Предыдущий/Следующий» → back-bar → похожие/ближайшие объекты.

- **Если фото объекта и так есть в галерее из текста (`gallery`/`extractGalleryAndCleanContent`), не дублировать его отдельной картинкой в intro сверху страницы** — на живых данных featured-изображение почти всегда совпадает с первым фото в тексте; в intro остаются только заголовок и мета (дата/место), фото пользователь видит один раз, в галерее. Действует и для Архитектуры, и для Городов — если у будущего модуля так же будет отдельный `imgSrc` **и** галерея из того же контента, тот же вывод применим сразу, без отдельного запроса пользователя.
- **breadcrumb размещать под hero-секцией, а не над ней**, если на странице есть полноэкранный hero с приёмом «уезжает под шапку» (`margin-top: -80px; padding-top: 80px`, как у `CatalogLayout.vue` и `CityTimelineView.vue`) — если поставить breadcrumb перед таким hero в обычном потоке, отрицательный отступ утянет hero поверх крошек и перекроет их. У страниц объекта/события с маленьким intro (без такого приёма) порядок обратный: breadcrumb идёт первым, как обычно.
- **Content-поле** — сырой HTML из WP. Относительные `../../wp-content/...` разворачивать в абсолютные через `SITE_URL` до любого дальнейшего парсинга.
- **Не все мета-поля с «датой» в названии — ISO-даты.** `hero_birth_date`/`hero_death_date` — обычная текстовая строка формата `дд.мм.гггг` (часть значений неполная, только год), а не WP-таймстемп. `new Date("07.11.1912").toLocaleDateString()` не бросает исключение (значит `try/catch` вокруг такого форматтера ничего не поймает) и не кидает ошибку в консоль — просто тихо возвращает `"Invalid Date"` прямо в вёрстку, воспроизводится только визуально. Такие поля выводить как есть, без прогона через `new Date()`; через него имеет смысл форматировать только настоящие ISO-поля вроде `post.date`/`comment.date` (см. `formatDate()` в `NewsView.vue`/`CommentsSection.vue` — те корректны, копировать их для текстовых дат не надо).
- **Галерея из текста**: фото в `content` свёрстаны вручную (без единого стандарта), подписи — обычно следующей строкой под картинкой. Парсить через `DOMParser` (устойчивее регулярок к такой вёрстке), а не строковыми регэкспами — см. `extractGalleryAndCleanContent` в `useAttractions.js`. Вырезанные из текста блоки убирать из `content` целиком (иначе фото задублируется — один раз в тексте, второй в карусели), и подчищать опустевшие пустые обёртки-разделители (иначе их суммарный `margin` даёт заметный пустой хвост).
- Карусель для такой галереи — общий вид с попапом карты (рамка, счётчик, стрелки, миниатюры, клик → `ImageLightbox`), плюс подпись под фото — см. `AttractionGallery.vue`.
- **Навигация «Предыдущий/Следующий»**: `grid-template-columns: minmax(0, 1fr) minmax(0, 1fr)`, **не** просто `1fr 1fr` — иначе длинный несжимаемый заголовок раздувает свою колонку сетки шире положенных 50%. Заголовок — `overflow:hidden; text-overflow:ellipsis; white-space:nowrap`, плюс `:title="item.title"` для полного текста в нативной подсказке при обрезке. На ≤767px «Предыдущий»/«Следующий» сокращаются до «Пред.»/«След.» — двумя `<span>` с переключением `display` по брейкпоинту, без JS.
- **Back-bar**: основная CTA-кнопка (`.cta-btn`, ochre, bracket-clip-path) слева + неприметная ссылка «Редактировать» справа (`justify-content: space-between` на контейнере уже даёт нужное выравнивание). Ссылка — на `{SITE_URL}wp-admin/post.php?post={id}&action=edit` (для объекта/термина CPT — `{SITE_URL}wp-admin/term.php?taxonomy={tax}&tag_ID={id}&post_type={post_type}`), `target="_blank"`, приглушённый цвет/opacity, не конкурирует по весу с основной кнопкой. Место на странице не жёстко зафиксировано после summary/галереи — если явно попросили поднять его выше (например, над длинным списком/лентой, а не в самом низу страницы), это тот же компонент, просто в другом месте разметки.
- **Похожие/ближайшие объекты** — сетка карточек `repeat(auto-fit, minmax(180px, 1fr))`, 1.5px dashed рамка, ховер: подъём + тень + ochre-рамка. Ранжирование — на сервере (см. ниже), не на клиенте. Бейдж в углу карточки — расстояние (гео) либо дата (хронологическое соседство, см. модуль «Города») в зависимости от смысла «рядом» у конкретного модуля; визуально один и тот же приём (тизел-пилюля). Если серверный `/nearby` возвращает окно, включающее само текущее событие (нужно для определения его позиции внутри окна) — на фронте отфильтровывать его из сетки (`computed`, не мутируя ответ), иначе карточка ссылается сама на себя.
- Ширина всех секций объектной страницы — унифицирована между модулями (`max-width: 1000px`), не подбирается заново под каждый модуль.

### REST-паттерны на бэкенде (`api/*/rest-api.php`)

- Bulk-эндпоинт списка — без пагинации, тяжёлые поля (`content`, аннотация) намеренно пустые в массовом ответе; подтягиваются отдельным запросом по id, когда пользователь открыл конкретный объект.
- `/{id}/adjacent` — предыдущий/следующий по возрастанию ID, опционально в рамках таксономии, если она есть у сущности.
- `/{id}/similar` (по совпадению таксономий/значимых слов), `/{id}/nearby` (по гео-расстоянию, формула гаверсинуса, **или** по соседству в упорядоченном списке — см. модуль «Города», где «рядом» значит по дате в рамках того же города, а не по километрам) — ранжирование кандидатов **на сервере**, отдаётся top-4/окно из нескольких соседей. Общая функция форматирования карточки для навигационных блоков (`format_xxx_nav_item`) переиспользуется между `/adjacent` и `/similar`|`/nearby`.
- Если сущность и так зарегистрирована с `show_in_rest => true`, деталь по id получать штатным `/wp/v2/{cpt}/{id}?_embed=1`, а не заводить свой кастомный `/objects/{id}` — кастомные роуты нужны только для списков/adjacent/nearby/similar, которых в стандартном REST нет (см. `useHistoryEvent`: одиночное событие идёт в `/wp/v2/history/{id}`, таксономия города достаётся из `_embedded['wp:term']`).
- Если у сущности есть таксономия, задающая естественную группировку (например, «Город» у `history`) и в рамках неё нужна строгая изоляция контента (лента времени только по одному городу) — adjacent/nearby фильтровать `tax_query` по этой таксономии, а не просто по возрастанию ID/даты по всей коллекции.
- Любые пороги/радиусы поиска (например, максимальная дистанция для «Объектов рядом») — обязательный параметр запроса с клиента, а не константа на сервере. На клиенте значение по умолчанию хранится в `window.__XXX__` в `index.html` (тот же принцип, что у `API_BASE_URL`/`YANDEX_MAPS_API_KEY`), не зашито в JS-бандле.
- Таксономия, которая используется только для группировки контента, а не для пользовательской фильтрации каталога (например, «Город» — переключение города идёт через отдельную страницу выбора, не через чипы фильтра) — не обязана быть в списке фильтров фронта просто потому, что она зарегистрирована в REST; это решение фронтенда, а не бэкенда.
- `api/` в этом репозитории — рабочая копия исходников плагинов реального сервера (`testsite.vyatgeo.ru`); правки переносятся на сервер **вручную по FTP** (не автоматически) — после правок дождаться подтверждения деплоя, прежде чем проверять живым запросом. Проверять новый PHP через `php -l` (в системе есть несколько версий в `/c/OSPanel/modules/php/`, актуальный синтаксис — через PHP 8.x, не 7.4) и затем сверять живым запросом через `curl`.
- **`save_post`-обработчик обязан выходить раньше своей логики при `defined('REST_REQUEST') && REST_REQUEST`.** При запросах через REST (SPA, скрипты импорта) `$_POST` всегда пуст — если хук читает `$_POST['field']` и, не найдя ключ, безусловно очищает meta (`else { update_post_meta($id, 'field', ''); }` — ровно так устроен унаследованный от `attraction` паттерн), то **любое** REST-обновление поста (даже не трогающее эти поля вовсе, например смену `title`) стирает все остальные его мета-поля до пустой строки. Обнаружено и исправлено во всех 7 плагинах (`attraction`, `artifact-finder`, `geopoints`, `history`, `geroi-vyatki`, `oopt-kirov`, `archeology`) — как в главном `save_post`, так и в аналогичных `created_{taxonomy}`/`edited_{taxonomy}` хуках term-meta (`headman`/`deep`/`workdate`/`worktype` в geopoints, `finding_type` в artifact-finder, `oopt_species` в oopt-kirov), если у них есть деструктивная `else`-ветка с `delete_term_meta`. Хуки term-meta без такой ветки (например, `city` в history) не нуждаются в этой правке — они и так не деструктивны, значения приходят через штатный REST term-meta независимо.
- **`update_callback` в `register_rest_field` не должен делать `if (!$value) return;`/`return 0;`** — эта охрана исторически задумывалась «не писать пустое значение», но на деле не даёт **очистить** поле через REST: `update_callback` вызывается WordPress только когда ключ реально присутствует в теле запроса (см. ниже про `null`), поэтому явная пустая строка в запросе — это осознанный запрос на очистку, а не «оставить как есть». Верная форма — `return update_post_meta($object->ID, $field_name, $value ?? '');` (для term-meta — `$object->term_id`, не `$object->ID`: у `WP_Term` такого свойства нет, есть только у `WP_Post`; эта путаница отдельно ловилась как самостоятельный баг в 4 term-meta полях `geopoints`, никак не связанный с REST).
- **Очистить поле через REST можно только пустой строкой `''`, не `null`.** PHP `isset()` считает явный `null` в JSON-теле отсутствующим ключом — `update_additional_fields_for_object()` в ядре WP пропускает вызов `update_callback` для таких полей вообще, значение остаётся прежним без единой ошибки в ответе. Это поведение самого WP REST API, не место для правки в плагине — учитывать на фронте/в клиентских скриптах.

## Паттерны сквозных фич (страницы, записи, комментарии, меню)

В отличие от модулей выше, эти фичи не привязаны к одному разделу — задействованы сразу в нескольких местах SPA и в самой теме WordPress.

### Общий шаблон WP-страницы (`PageView.vue`)

- Один компонент обслуживает и `/page/:slug` (динамический slug пропом, `props: true` в роуте), и `/about` (slug зафиксирован статично, `props: { slug: 'about' }`) — не форкать под конкретную страницу, расширять HTML-классами в контенте (см. ниже), а не новыми компонентами.
- Hero — заголовок страницы + фон: featured image страницы (`_embed=1` в `usePage.js`, тот же фолбэк-паттерн по размерам, что и в других модулях: `medium_large -> large -> media.source_url`), либо дефолтная картинка шаблона, если фото не привязано.
- Маршруты с hero **не должны** иметь `meta: { headerSolid: true }` — иначе шапка теряет прозрачность/блюр поверх hero-фото (тот же принцип, что у `/` и `/cities/:citySlug`); этот флаг остаётся только у страниц без hero (объектные/событийные страницы, `/news/:id`).
- Свободный HTML-контент WP-страницы стилизуется предопределёнными классами (`.content :deep(...)` в `PageView.vue`): `h2`/`h3`/`ul` — базовая типографика; `.stat-grid`/`.stat-card` — карточки статистики; `.module-grid`/`.module-card` — сетка карточек-ссылок; `.cta-block`/`.cta-btn` — призыв к действию (та же кнопка-скоба, что и везде на сайте). Любая новая WP-страница может переиспользовать эти классы в своём контенте, не только «О проекте».
- **`wpautop()` вставляет `<br>` между соседними строками контента, если они не разделены блочным тегом.** У `<div class="stat-card">` (блочный тег) это не сработало, у `<a class="module-card">` (строчный) — сработало, вставив `<br>` между каждой парой ссылок и сломав сетку лишними ячейками. Если контент генерируется программно (как `nv_spa_ensure_about_page()`), последовательность строчных тегов внутри одного грид-контейнера писать одной строкой без переносов, не одну ссылку на строку.

### Комментарии (`useComments.js`, `CommentsSection.vue`)

- WP-ядро по умолчанию блокирует **анонимный** `POST /wp/v2/comments` (401 `rest_comment_login_required`) независимо от настройки «Разрешить комментарии» в Обсуждении — это отдельная проверка, фильтр `rest_allow_anonymous_comments` (default `false`), который относится только к REST API. Тема явно включает его в `functions.php`; без этого гостевая отправка не работает вообще ни для одной сущности.
- Код ошибки нужно читать из тела ответа **раньше** общей ветки по HTTP-статусу: `rest_comment_closed` (у конкретной записи закрыты комментарии) приходит тем же статусом 403, что и общий запрет анонимных запросов — если проверять `res.status === 403` первым, ветка `'closed'` в UI никогда не сработает и пользователь видит общее сообщение вместо точного.
- **Залогиненный в WP посетитель отправляет POST так же анонимно, как и гость, если не передать `X-WP-Nonce`.** Браузер шлёт куку сессии на любой fetch к тому же домену независимо от того, ждём мы этого или нет; без nonce WP либо вовсе не распознаёт пользователя (`GET /wp/v2/users/me` без nonce отдаёт 401, как для анонима), либо отклоняет запись (403) — то есть без этого залогиненный в WP пользователь не смог бы отправить комментарий с сайта вообще. `nv_spa_user_script()` в `functions.php` выводит `window.__WP_REST_NONCE__` (только когда `is_user_logged_in()`), `REST_NONCE` в `src/config/api.js` его читает; `useComments.js` подставляет заголовок в `postComment`, если он есть.
- Форма комментариев автоподставляет имя/e-mail: у залогиненного — из `GET /wp/v2/users/me?context=edit` (`useCurrentUser()`, тот же nonce; `context=edit` обязателен — в `view` WP не отдаёт e-mail даже для себя), у гостя — из `localStorage` (`loadGuestAuthor`/`saveGuestAuthor`, ключ `nv_comment_author`), сохраняются туда только после **успешной** отправки и только если пользователь не залогинен.

### Меню (`useMenu.js`, `menu-api.php`)

- Собственный REST-роут `nv/v1/menu/{location}` (не core `/wp/v2/menu-items`, который требует `edit_theme_options`) — публичный, без правок бэкенда под каждое новое меню. Контракт — `api/docs/menu.md`.
- Локация `spa_primary` (шапка) — при активации темы создаётся дефолтное меню, если локации ещё не назначено меню (`nv_spa_ensure_default_menu()` в `functions.php`).
- `SiteHeader.vue` монтирует `useMenu('spa_primary')` → если WP-меню непустое — рендерит его пункты, если пустое или запрос упал — фолбэчит на захардкоженный список `HARDCODED_NAV`. Внешние ссылки (абсолютный URL не на этот домен) — `<a>` вместо `<RouterLink>`. Активный пункт — сверка `item.to === $route.path`. Мобильное меню (сайдбар) рендерит тот же массив пунктов.

### Классические WP-пермалинки -> маршруты SPA (`nv_spa_resolve_wp_permalink_redirect()` в `functions.php`)

- Ссылки внутри `content.rendered`, комментариев и т.п. иногда указывают на настоящие WP-пермалинки — `?p=123`, `?page_id=123`, `?attachment_id=123`, `?attraction=slug`, `?finding=slug`, `?history=slug`, `?city=slug`, `?archeology=slug` при «Простых» ссылках, либо `/archives/attraction/slug`, `/archives/archeology/slug`, `/archives/123`, `/test` при «Числовых» — SPA их не генерирует и не понимает. К моменту `template_redirect` WP уже резолвил объект штатным `WP_Query`, поэтому `is_singular()`/`is_tax()`/`is_attachment()` + `get_queried_object()` дают тот же результат независимо от текущего `permalink_structure` — резолвер не привязан к конкретному формату URL. 302-редиректит на `/news/{id}`, `/page/{slug}`, `/architecture/{id}`, `/ethnography/{id}`, `/archeology/{id}`, `/cities/{city}/event/{id}`, `/cities/{slug}`.
- Резолвер обязан сравнивать итоговый путь с текущим запрошенным перед редиректом — без этого страница, чей реальный WP-пермалинк совпадает с её же SPA-маршрутом (сейчас единственный случай — `/about`), зациклила бы 302 сама на себя.
- Тип записи без собственного маршрута в SPA (`geopoints` и т.п.) — резолвер возвращает `null` и просто отдаёт SPA-шелл как обычно, ничего не угадывая.
- **Вложение-«сирота» (медиафайл без родительской записи) по умолчанию у WP живёт на одном сегменте URL, совпадающем со slug'ом файла** (`/%postname%/`, как у страниц) — если в медиатеку когда-либо загрузят файл, чьё имя совпадает с одним из корневых маршрутов SPA (например, `nature.jpg` → вложение со slug `nature`), WP резолвит `is_attachment()` для `/nature` раньше, чем до этого пути дошла бы очередь у SPA, и резолвер (в его собственной логике «нет родителя — ведём на файл вложения») увёл бы весь раздел «Природа» на картинку. Guard — `nv_spa_is_reserved_route_root($request_path)`: если первый сегмент запрошенного пути совпадает с одним из зарезервированных корневых маршрутов SPA (`victory`, `ethnography`, `cities`, `nature`, `archeology`, `architecture`, `about`, `news`, `page`, `archives` — список поддерживается вручную, обновлять при добавлении нового корневого раздела), редирект на файл вложения пропускается, отдаётся обычный SPA-шелл. Для всех остальных вложений-сирот (не совпадающих с маршрутами SPA) редирект на файл по-прежнему работает как раньше — это реальный сценарий (старая прямая ссылка на файл из контента), а не баг.
- **`permalink_structure` не должен быть «Простые ссылки» (`?p=123`)** — тогда `.htaccess` не содержит catch-all rewrite-правила вообще, и Apache отдаёт 404 на любой SPA-путь ещё до PHP; никаким кодом это не чинится, только настройкой. Любая непустая структура («Числовые», «Название записи» и т.д.) работает. В Docker-окружении `permalink_structure` периодически сбрасывается сам по себе — если SPA вдруг перестал отвечать, первым делом проверить **Настройки → Постоянные ссылки** и просто сохранить их заново (или `wp rewrite flush --hard` + повторный запуск `ensure-htaccess.sh`).

### Featured image для WP-страниц

Тема объявляет `add_theme_support('post-thumbnails')` + `add_post_type_support('page', 'thumbnail')` в `nv_spa_theme_setup()` — без первого редактор вообще не видит панель «Изображение записи» ни у одного типа записи (у attraction/finding/history фото исторически попадали через импорт-скрипты, минуя админку), без второго — конкретно у `page`, потому что `thumbnail` не входит в её `supports` по умолчанию (в отличие от `post`). Используется как фон hero в `PageView.vue`.

## Правила работы

- Все цвета — через CSS-переменные (`var(--color-*)`), без хардкода. Отступы — через `var(--space-*)`.
- Типографика: Playfair Display (заголовки, вес 700) + Roboto Slab (весь остальной текст). Курсив/малые начертания Playfair — только для декоративных/цитатных случаев, не для обычного текста.
- Не использовать цветной `border-left`/`border-right` толще 1px как декоративный акцент на карточках/блоках — частый «AI-tell», сайт использует пунктирную 1.5px рамку как единственный декоративный приём.
- Отзывчивость: breakpoints 1023px и 767px. `min-height`/`min-width: 44px` на кнопках, чипах и интерактивных ссылках (WCAG touch target).
- Анимации — CSS transitions/transform, `prefers-reduced-motion` отключает их глобально (`base.css`).
- WCAG AA: контраст 4.5:1, `focus-visible` на всех интерактивных элементах (глобальный стиль уже есть в `base.css`, переопределять только при необходимости).
- После правок в `.vue`-файлах — прогонять детектор скилла `impeccable` и `npm run build`, прежде чем считать задачу завершённой.
