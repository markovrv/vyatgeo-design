# Проект «Наследие Вятки» (Vue-версия)

Историко-культурное наследие Кировской области — сайт к 90-летию региона (1936–2026). Эта директория (`naslediye-vyatki/`) — рабочая Vue 3 + Vite реализация; статический HTML-прототип в корне репозитория (`../index.html`, `../*.html`, `project/*.dc.html`) сохранён только для референса дизайна и не разрабатывается дальше.

## Структура

```
src/

  router/index.js        # lazy-loaded маршруты
  config/

    maps.js               # YANDEX_MAPS_API_KEY из window.__YANDEX_MAPS_API_KEY__

  composables/

    useFindings.js        # модуль «Этнография» — реальный WP REST API
```

  style.css               # заголовок темы для WordPress

На сегодня с реальным API интегрированы 3 из 7 модулей — **Архитектура** (`attraction`), **Этнография** (`artifact-finder`/findings) и **Города** (`history` + таксономия `city`: лента времени по городам с пагинацией/поиском, карточки и hero городов, реальная Яндекс.Карта с пинами-городами, координаты и мини-карта в админке термина). Остальные (VictoryFaces, Nature, Archeology) — на статичных моковых данных, интеграция не начата. Блок «Вятский край: семь веков истории» на главной (`IndexView.vue`) тоже не статика — вехи подтягиваются из реальных событий Кирова (`useHistoryMilestones`, см. ниже).

## Тема WordPress (SPA Shell)

Тема `wp-theme/naslediye-vyatki-theme/` — минимальная оболочка для headless-режима: отключает стандартный вывод WP и отдаёт собранный Vue-билд (`dist/index.html`) на все фронтовые URL. `wp-admin`, `wp-login.php`, `/wp-json/` тема не трогает.

### Customizer API

Конфигурация SPA (API-адрес, ключ Яндекс.Карт, радиус поиска) вынесена в Customizer (**Внешний вид → Настроить → Конфигурация приложения**) и не требует правки `dist/index.html`:

| Настройка | `theme_mod` | Переменная |
|---|---|---|
| API Base URL | `nv_api_base_url` | `window.__API_BASE_URL__` |
| Yandex Maps API Key | `nv_yandex_maps_api_key` | `window.__YANDEX_MAPS_API_KEY__` |
| Радиус «Объекты рядом» (км) | `nv_attraction_nearby_radius_km` | `window.__ATTRACTION_NEARBY_RADIUS_KM__` |

Принцип работы: `nv_spa_render_app()` читает `dist/index.html`, вставляет `<script>`-блок со значениями из `get_theme_mod()` перед `</head>` и отдаёт результат. Customizer-скрипт выполняется после дефолтного `<script>` из `index.html`, переопределяя `window.__*__`. `transport: 'refresh'` — страница перезагружается при сохранении.

### Docker (локальное тестирование темы)

```bash
cd wp-theme
docker compose up -d       # WordPress + MariaDB на порту 8080
docker compose down         # остановка
docker compose down -v      # остановка + удаление БД
```

- Фронтенд/SPA: http://localhost:8080
- Админка: http://localhost:8080/wp-admin/
- Тема монтируется из локальной папки — правки в `functions.php` применяются без пересборки контейнера
- `.htaccess` с mod_rewrite генерируется автоматически скриптом `ensure-htaccess.sh` (без него статика `/assets/*` не доходит до WordPress)

Для пересоздания контейнера после правок в `docker-compose.yml`:
```bash
docker compose up -d --force-recreate wordpress
```

## Паттерны модулей с реальным API

Ниже — то, что уже устоялось в интегрированных модулях (Архитектура, Этнография, Города) и стоит повторять один в один при подключении следующего модуля к реальному API, а не изобретать заново.

### Composables (`src/composables/use*.js`)

- Список: `useXxxs()` → `{ items, loading, error, fetchXxxs }`. Один объект: `useXxx()` → `{ item, loading, error, fetchXxx(id) }`. Никогда не бросают наружу исключения — ошибка складывается в `error.value`, компонент сам решает, что показать.
- Состояние каталога — реактивный **module-level singleton** (`export const xxxCatalogState = reactive({...})`), а не `ref` внутри компонента: так фильтр/страница/scrollY переживают переход на страницу объекта и возврат назад. Восстановление скролла — через `onBeforeRouteLeave` (сохранить) + `onMounted` (`nextTick` + `requestAnimationFrame` дважды, чтобы дождаться реального рендера, затем `window.scrollTo`).
- `SITE_URL` (домен без `wp-json/`) экспортируется рядом с `API_BASE_URL` — нужен и для относительных URL в HTML-контенте (`../../` → абсолютный), и для ссылок в `wp-admin`.
- Заголовки WP иногда приходят с буквальными HTML entity-кодами (`&#8212;`) — раскрывать вручную через скрытый `<textarea>` (`decodeEntities`), сервер это не делает.
- Если у сущности нет своих таксономий (как у `attraction`) — не выдумывать фильтры на фронте, которых нет в данных.

### Каталог (`CatalogLayout.vue`)

- Слоты: `#heading`, `#description`, `#filters`, `#map`, `#grid`, `#pagination`. Общий для всех модулей компонент, его вёрстку под конкретный модуль не форкать — расширять через слоты.
- Переключатель «Карта/Каталог» + поиск — единый узнаваемый паттерн сайта: `FilterBar` (пунктирные пилюли-чипы, 1.5px dashed, ochre-заливка на активном) + `.search-box` (сплошная рамка 1.5px, радиус `var(--radius)`, ochre-обводка по фокусу, `min-height: 44px`) — см. `AttractionControls.vue`. Не изобретать новый стиль тумблера/инпута под очередной модуль.
- Если карте нужен весь набор данных сразу (кластеризация не работает постранично) — грузить всю коллекцию одним запросом, а каталожный вид фильтровать/пагинировать **на клиенте** поверх этого же массива, а не городить серверную пагинацию только ради второго режима просмотра.
- **Исключение** — если у вида нет карты и датасет большой (лента времени Кирова — 666+ записей на один город): грузить постранично с сервера (`page`/`per_page`, по 10 штук) и подгружать по мере прокрутки через `IntersectionObserver` на пустом sentinel-элементе в конце списка, а не разом. Век/поиск в этом случае — **тоже серверные параметры** (`meta_query`/`s` в `WP_Query`), не клиентский фильтр поверх уже загруженного куска: иначе первая страница при активном фильтре могла бы прийти пустой, хотя подходящие записи есть дальше. Кэш уже загруженных страниц и текущий фильтр — module-level singleton (как и остальное состояние каталога), при возврате со страницы объекта показывает то же самое, а не сбрасывается к первой странице (см. `historyEventsCache`/`historyTimelineState` в `useHistory.js`).
- Локальный «Загрузка…» при смене фильтра/поиска должен закрывать **только список результатов**, а не всю страницу через общий верхний `v-if="loading"` — если под этот же флаг попадает ещё и герой/шапка/панель управления, при каждой смене фильтра страница схлопывается до одной строки текста, браузер обрезает scrollY по новой (маленькой) высоте документа, и после перерисовки страница остаётся наверху, а не там, где был пользователь. Нужны раздельные `loading`-флаги: один — «страница/город ещё не загружены вообще» (гейтит всю страницу), другой — «текущий список перезагружается» (гейтит только список). Массив элементов при этом не обнулять сразу на время запроса — старые результаты остаются на экране до прихода новых, тогда смена фильтра/поиска ощущается мгновенной, без схлопывания и «прыжка» прокрутки (см. `CityTimelineView.vue`).
- Bulk-эндпоинты часто отдают только маленькую WP-миниатюру (обычно 150×150) — той же самой, что используется для пинов карты. Для карточек шире ~300px она размывается. Решение — батч-запросом взять готовый размер получше: `GET /wp/v2/media?include=id1,id2,...&_fields=id,media_details` (именно так, без вложенных путей вида `media_details.sizes.large` — WP тихо режет такие вложенные `_fields` и отдаёт пустой объект вместо ошибки), один запрос на видимую страницу каталога, не на каждую карточку отдельно (см. `useAttractionThumbnails`).
  - **Цепочка фолбэка обязана доходить до оригинала**: `medium_large` → `large` → `medium` → `full`, и только если во всём объекте `sizes` вообще пусто — оставлять миниатюру из массового ответа. WP генерирует размер, только если оригинал больше его порога, поэтому у части объектов (на живых данных Архитектуры — 62 из 423, то есть ~15%) `medium_large` (768px) и `large` (1024px) отсутствуют одновременно, потому что оригинал изначально мельче. Если остановиться на `medium_large → large → null`, эти ~15% молча откатываются на 150×150 и размытость вылезает точечно, уже после релиза — воспроизвести на глаз на паре тестовых объектов почти невозможно, нужно было проверить весь набор через `/wp/v2/media` вручную, чтобы поймать. Не сокращать цепочку ради лаконичности кода.
  - **Справочник `id вложения → URL` из батч-апгрейда не должен жить в локальном `ref` внутри composable**, если на страницу можно вернуться после перехода на объект: composable вызывается заново при каждом монтировании компонента, `ref` создаётся пустым, а вотчер на список элементов повторно не срабатывает (сам список элементов часто берётся из уже готового module-level кэша и не меняется) — миниатюры молча откатываются на 150×150 при возврате. Справочник должен быть module-level `ref` (переживает переход туда-обратно) и дополнительно зеркалироваться в `sessionStorage` (переживает и перезагрузку вкладки) — при записи в `sessionStorage` не дублировать в каждой записи домен, которого и так знает `SITE_URL`: хранить путь без домена, разворачивать в абсолютный URL при чтении (см. `historyThumbnailsCache`/`toRelativeUrl`/`toAbsoluteUrl` в `useHistory.js`).

### Карта (`AttractionMap.vue`, `vue-yandex-maps`)

- `initYmaps()` перед монтированием дочерних компонентов карты — у библиотеки бывает гонка при обычном автоинициализирующем монтировании.
- Кластеризация — `yandex-map-clusterer` с кастомной иконкой; кастомные маркеры — через `yandex-map-marker` со слотом.
- Кастомные контролы (`yandex-map-control-button`): обёртка библиотеки добавляет свой фиксированный паддинг (~8px с каждой стороны) поверх заданного размера вложенного контента — если нужен точный итоговый размер кнопки (как у соседних штатных контролов), считать размер вложенного `<span>` в обратную сторону (итог минус паддинг с двух сторон), а не выставлять размер самого контрола. Подсказка — своя всплывающая карточка в стиле проекта, не полагаться на нативный `title` (плохо стилизуется).
- Полноэкранный просмотр фото — всегда через переиспользуемый `ImageLightbox.vue` (зум, яркость/контраст, клавиатура, счётчик уже реализованы там). Не дублировать эту логику внутри очередного попапа/карусели — просто открывать `ImageLightbox` по клику на фото.
  - **В `ImageLightbox.vue` зум сделан явным пересчётом ширины/высоты картинки в пикселях** (`computeFitSize` по `naturalWidth/Height` + размеру контейнера), а не `transform: scale()` с `object-fit: contain`: `object-fit` не меняет layout-размер элемента, поэтому в момент пересечения `scale > 1` картинка «прыгала» на свой натуральный (часто в разы больший) пиксельный размер. Центрирование содержимого сделано через `margin: auto` на самой картинке, а не `align-items/justify-content: center` на скролл-контейнере — иначе переполнение в сторону начала осей (верх/лево) недоступно прокруткой ни в одном браузере, это общая особенность flexbox-центрирования с `overflow: auto`. Зум «от точки» (курсор/центр экрана остаётся на месте) реализован прямым пересчётом `scrollLeft/scrollTop`, а не CSS `transform-origin`. Не возвращаться к `transform: scale` + `transform-origin` для зума — оба бага уже были пойманы и исправлены один раз.
- Панель управления (переключатель + поиск) на карте — floating-плашка поверх карты в режиме карты, и та же панель обычной строкой над сеткой в режиме каталога (один компонент, два визуальных состояния через модификатор класса). Отступы от краёв — одинаковые в обоих режимах, чтобы при переключении режима элементы не «прыгали» по горизонтали. Паттерн общий на все модули с картой (не только Архитектура) — см. также `HistoricCitiesView.vue`.
- **Лёгкий вариант карты** (без кластеризации/исторических слоёв/попапа — просто пины с фото и переходом по клику, как у городов на `HistoricCitiesView.vue`/`HistoryCitiesMap.vue`) не нужно собирать из полной версии `AttractionMap.vue` вырезанием лишнего — отдельный маленький компонент с тем же набором примитивов (`YandexMap`, `YandexMapMarker`, `initYmaps`, `fitToPoints` по bounds точек) читается проще, чем `AttractionMap.vue` с закомментированными кусками.
- **Координаты для сущностей без своего REST-эндпоинта записи** (таксономия, а не CPT — например, «Город») хранятся term meta-полем `"lat, lng"` строкой, тем же форматом, что и `attraction_coord`/`geopoints_coord` у CPT. Мини-карта для ввода координат в редакторе термина — тот же классический Yandex Maps JS API v2.1 (`ymaps.Map`/`ymaps.GeoObject`, НЕ `vue-yandex-maps`/ymaps3, который используется только во Vue-фронте) и тот же скрипт-паттерн, что и в админке Архитектуры/Гео-точек (`api/attraction/js/adminMap.js`, `api/geopoints/js/adminMap.js`) — клик по карте и ручной ввод в текстовое поле синхронно обновляют друг друга. Копия скрипта на таксономию — `api/history/js/adminCityMap.js`, подключается только на экранах добавления/редактирования термина (enqueue внутри колбэков `{tax}_add_form_fields`/`{tax}_edit_form_fields`), а не глобально.

### Страница объекта (`{Module}ItemView.vue` / `{Module}ObjectView.vue`)

Общая структура сверху вниз: breadcrumb → intro (заголовок + место) → summary/content → галерея → навигация «Предыдущий/Следующий» → back-bar → похожие/ближайшие объекты.

- **Если фото объекта и так есть в галерее из текста (`gallery`/`extractGalleryAndCleanContent`), не дублировать его отдельной картинкой в intro сверху страницы** — на живых данных featured-изображение почти всегда совпадает с первым фото в тексте; в intro остаются только заголовок и мета (дата/место), фото пользователь видит один раз, в галерее. Действует и для Архитектуры, и для Городов — если у будущего модуля так же будет отдельный `imgSrc` **и** галерея из того же контента, тот же вывод применим сразу, без отдельного запроса пользователя.
- **breadcrumb размещать под hero-секцией, а не над ней**, если на странице есть полноэкранный hero с приёмом «уезжает под шапку» (`margin-top: -80px; padding-top: 80px`, как у `CatalogLayout.vue` и `CityTimelineView.vue`) — если поставить breadcrumb перед таким hero в обычном потоке, отрицательный отступ утянет hero поверх крошек и перекроет их. У страниц объекта/события с маленьким intro (без такого приёма) порядок обратный: breadcrumb идёт первым, как обычно.
- **Content-поле** — сырой HTML из WP. Относительные `../../wp-content/...` разворачивать в абсолютные через `SITE_URL` до любого дальнейшего парсинга.
- **Галерея из текста**: фото в `content` свёрстаны вручную (без единого стандарта), подписи — обычно следующей строкой под картинкой. Парсить через `DOMParser` (устойчивее регулярок к такой вёрстке), а не строковыми регэкспами — см. `extractGalleryAndCleanContent` в `useAttractions.js`. Вырезанные из текста блоки убирать из `content` целиком (иначе фото задублируется — один раз в тексте, второй в карусели), и подчищать опустевшие пустые обёртки-разделители (иначе их суммарный `margin` даёт заметный пустой хвост).
- Карусель для такой галереи — общий вид с попапом карты (рамка, счётчик, стрелки, миниатюры, клик → `ImageLightbox`), плюс подпись под фото — см. `AttractionGallery.vue`.
- **Навигация «Предыдущий/Следующий»**: `grid-template-columns: minmax(0, 1fr) minmax(0, 1fr)`, **не** просто `1fr 1fr` — иначе длинный несжимаемый заголовок раздувает свою колонку сетки шире положенных 50%. Заголовок — `overflow:hidden; text-overflow:ellipsis; white-space:nowrap`, плюс `:title="item.title"` для полного текста в нативной подсказке при обрезке. На ≤767px «Предыдущий»/«Следующий» сокращаются до «Пред.»/«След.» — двумя `<span>` с переключением `display` по брейкпоинту, без JS.
- **Back-bar**: основная CTA-кнопка (`.cta-btn`, ochre, bracket-clip-path) слева + неприметная ссылка «Редактировать» справа (`justify-content: space-between` на контейнере уже даёт нужное выравнивание). Ссылка — на `{SITE_URL}wp-admin/post.php?post={id}&action=edit` (для объекта/термина CPT — `{SITE_URL}wp-admin/term.php?taxonomy={tax}&tag_ID={id}&post_type={post_type}`), `target="_blank"`, приглушённый цвет/opacity, не конкурирует по весу с основной кнопкой. Место на странице не жёстко зафиксировано после summary/галереи — если явно попросили поднять его выше (например, над длинным списком/лентой, а не в самом низу страницы), это тот же компонент, просто в другом месте разметки.
- **Похожие/ближайшие объекты** — сетка карточек `repeat(auto-fit, minmax(180px, 1fr))`, 1.5px dashed рамка, ховер: подъём + тень + ochre-рамка. Ранжирование — на сервере (см. ниже), не на клиенте. Бейдж в углу карточки — расстояние (гео) либо дата (хронологическое соседство, см. модуль «Города») в зависимости от смысла «рядом» у конкретного модуля; визуально один и тот же приём (тизел-пилюля). Если серверный `/nearby` возвращает окно, включающее само текущее событие (нужно для определения его позиции внутри окна) — на фронте отфильтровывать его из сетки (`computed`, не мутируя ответ), иначе карточка ссылается сама на себя.
- Ширина всех секций объектной страницы — унифицирована между модулями (`max-width: 1000px`), не подбирается заново под каждый модуль.

### REST-паттерны на бэкенде (`api/*/rest-api.php`)

- Bulk-эндпоинт списка — без пагинации, тяжёлые поля (`content`, аннотация) намеренно пустые в массовом ответе; подтягиваются отдельным запросом по id, когда пользователь открыл конкретный объект.
- `/{id}/adjacent` — предыдущий/следующий по возрастанию ID, опционально в рамках таксономии, если она есть у сущности.
- `/{id}/similar` (по совпадению таксономий/значимых слов), `/{id}/nearby` (по гео-расстоянию, формула гаверсинуса, **или** по соседству в упорядоченном списке — см. модуль «Города», где «рядом» значит по дате в рамках того же города, а не по километрам) — ранжирование кандидатов **на сервере**, отдаётся top-4/окно из нескольких соседей. Общая функция форматирования карточки для навигационных блоков (`format_xxx_nav_item`) переиспользуется между `/adjacent` и `/similar`|`/nearby`.
- Если сущность и так зарегистрирована с `show_in_rest => true`, деталь по id получать штатным `/wp/v2/{cpt}/{id}?_embed=1`, а не заводить свой кастомный `/objects/{id}` — кастомные роуты нужны только для списков/adjacent/nearby/similar, которых в стандартном REST нет (см. `useHistoryEvent`: одиночное событие идёт в `/wp/v2/history/{id}`, таксономия города достаётся из `_embedded['wp:term']`).
- Если у сущности есть таксономия, задающая естественную группировку (например, «Город» у `history`) и в рамках неё нужна строгая изоляция контента (лента времени только по одному городу) — adjacent/nearby фильтровать `tax_query` по этой таксономии, а не просто по возрастанию ID/даты по всей коллекции.
- Любые пороги/радиусы поиска (например, максимальная дистанция для «Объектов рядом») — обязательный параметр запроса с клиента, а не константа на сервере. На клиенте значение по умолчанию хранится в `window.__XXX__` в `index.html` (тот же принцип, что у `API_BASE_URL`/`YANDEX_MAPS_API_KEY`), не зашито в JS-бандле.
- Таксономия, которая используется только для группировки контента, а не для пользовательской фильтрации каталога (например, «Город» — переключение города идёт через отдельную страницу выбора, не через чипы фильтра) — не обязана быть в списке фильтров фронта просто потому, что она зарегистрирована в REST; это решение фронтенда, а не бэкенда.
- `api/` в этом репозитории — рабочая копия исходников плагинов реального сервера (`testsite.vyatgeo.ru`), правки здесь применяются сразу. Проверять новый PHP через `php -l` (в системе есть несколько версий в `/c/OSPanel/modules/php/`, актуальный синтаксис — через PHP 8.x, не 7.4) и затем сверять живым запросом через `curl`.

## Правила работы

- Все цвета — через CSS-переменные (`var(--color-*)`), без хардкода. Отступы — через `var(--space-*)`.
- Типографика: Playfair Display (заголовки, вес 700) + Roboto Slab (весь остальной текст). Курсив/малые начертания Playfair — только для декоративных/цитатных случаев, не для обычного текста.
- Не использовать цветной `border-left`/`border-right` толще 1px как декоративный акцент на карточках/блоках — частый «AI-tell», сайт использует пунктирную 1.5px рамку как единственный декоративный приём.
- Отзывчивость: breakpoints 1023px и 767px. `min-height`/`min-width: 44px` на кнопках, чипах и интерактивных ссылках (WCAG touch target).
- Анимации — CSS transitions/transform, `prefers-reduced-motion` отключает их глобально (`base.css`).
- WCAG AA: контраст 4.5:1, `focus-visible` на всех интерактивных элементах (глобальный стиль уже есть в `base.css`, переопределять только при необходимости).
- После правок в `.vue`-файлах — прогонять детектор скилла `impeccable` и `npm run build`, прежде чем считать задачу завершённой.
