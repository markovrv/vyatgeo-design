# Промпт для ИИ-агента: базовый функционал WordPress API в SPA — страницы, записи, комментарии, меню

## 0. Контекст

Проект «Наследие Вятки» — Vue 3 + Vite SPA (`naslediye-vyatki/src/`), headless-фронтенд к WordPress (`testsite.vyatgeo.ru/wp-json/`). Три модуля уже полностью интегрированы с реальным REST API (Архитектура/`attraction`, Этнография/`finding`, Города/`history`) — их composables (`src/composables/use*.js`) и вьюхи (`src/views/*View.vue`) задают устоявшийся паттерн, который эта задача обязана повторять, а не изобретать заново. Прочитай `CLAUDE.md` в корне `naslediye-vyatki/` перед началом — там описаны все конвенции (module-level singleton state, `SITE_URL`/`API_BASE_URL`, `decodeEntities`, разворачивание относительных URL в контенте, `ImageLightbox`, структура страницы объекта) и это обязательные к повторению паттерны, не рекомендации.

Сейчас в SPA нет: (1) вывода нативных WordPress-страниц (`page`) и записей (`post`) — только кастомные CPT-модули; (2) комментариев к любой сущности; (3) связи навигационного меню (`SiteHeader.vue`) с меню, редактируемым в WordPress — `navItems` в `SiteHeader.vue` захардкожен как JS-массив.

Задача — добавить все три возможности. Ниже — принятые решения по архитектуре (не варианты на выбор агента, а результат уже сделанного выбора) и детальный контракт.

---

## 1. Страницы (`page`)

Нативный `page` в WP уже публично доступен через `/wp/v2/pages` без каких-либо изменений на бэкенде (никакого `api/`-плагина не требуется).

- **Composable** `src/composables/usePage.js`: `usePage()` → `{ page, loading, error, fetchPage(slug) }`. Никогда не бросает исключения наружу — ошибка в `error.value`, как во всех остальных composables (см. `useAttraction()` в `useAttractions.js` для образца структуры).
  - Запрос: `GET {API_BASE_URL}wp/v2/pages?slug={slug}&_fields=id,title,content,slug`, затем при необходимости полного контента — тот же объект уже содержит `content.rendered` (пагинации/эмбедов для страницы не нужно).
  - `content.rendered` — сырой HTML, обязательно прогнать через то же разворачивание относительных `../../` → `SITE_URL`, что и в `useAttractions.js`/`useFindings.js`/`useHistory.js` (переиспользовать существующую утилиту `resolveRelativeUrls`, вынеся её в общий модуль — см. §5 про дублирование).
  - `decodeEntities` — на заголовок, тем же способом, что и в остальных composables.
- **View** `src/views/PageView.vue`, роут `/page/:slug` в `src/router/index.js`. Простая структура: breadcrumb → заголовок → content. Ширина секции — `max-width: 1000px`, как у остальных объектных страниц (см. правило про унификацию ширины в `CLAUDE.md`).
- Если `fetchPage` не находит страницу (пустой массив в ответе) — показать стандартный блок "не найдено" с ссылкой на главную (проверить, есть ли уже такой паттерн у ошибок 404 в других `*ItemView.vue`, и переиспользовать его, а не придумывать новый).
- **Не переносить** существующую статичную `AboutView.vue` на этот механизм в рамках этой задачи — она вне скоупа, только новый универсальный `/page/:slug` для произвольных WP-страниц (например, будущие «Контакты», «Политика конфиденциальности»).

## 2. Записи (`post`) — раздел «Новости»

Нативный `post` тоже публично доступен через `/wp/v2/posts` без изменений на бэкенде.

- **Composables** `src/composables/usePosts.js` (список) и `usePost.js` (один пост) — по образцу `useFindings.js`: список — постраничный запрос к `/wp/v2/posts?page=N&per_page=10&_embed=1` (посты потенциально многочисленны и растут во времени, как лента событий города — см. в `CLAUDE.md` пункт про исключение с серверной пагинацией для больших лент; **не** грузить всё разом ради карты, у постов карты нет вообще).
  - Состояние каталога — module-level singleton `export const postsCatalogState = reactive({ search: '', page: 1, ... })`, переживает переход на страницу поста и обратно (тот же принцип, что у `attractionCatalogState`/`historyTimelineState`).
  - Поиск — серверный параметр `search=` в `/wp/v2/posts`, не клиентская фильтрация уже загруженного (см. правило в `CLAUDE.md` про серверные параметры для больших лент).
  - `usePost()` → `{ post, loading, error, fetchPost(id) }`, деталь через `/wp/v2/posts/{id}?_embed=1`, featured-изображение — из `_embedded['wp:featuredmedia']`.
- **Views**: `NewsView.vue` (каталог через `CatalogLayout.vue`, слоты `#heading`/`#filters`/`#grid`/`#pagination`, **без** `#map` — у постов карты нет, слот просто не используется) и `NewsItemView.vue` (структура объектной страницы — см. §0: breadcrumb → intro → content → back-bar; без «похожих/ближайших» блока, если для постов не заведён `/adjacent`/`nearby` на бэкенде — это не требуется данной задачей).
- Роуты: `/news`, `/news/:id`.
- Добавить пункт «Новости» в навигацию (см. §4 — через меню WP, а не хардкодом, если раздел меню уже подключён; если пункт нужен до того, как редактор создаст его в WP-меню, оставить временный фолбэк-пункт в захардкоженном списке, см. §4).

## 3. Комментарии — чтение + отправка гостем, для всех сущностей с открытыми комментариями

### 3.1. Что уже готово на бэкенде

Все CPT в `api/*/register-*.php` (attraction, hero, oopt) уже зарегистрированы с `supports => [...,'comments',...]`, значит WP core сам добавляет в REST-схему `/wp/v2/{cpt}/{id}` поля `comment_status` (`open`/`closed`) и `ping_status` — **без каких-либо правок бэкенда**. Проверить это для `finding`/`history` (`api/artifact-finder/register-attraction.php`, `api/history/history.php`) и для нативных `post`/`page` — если у какого-то CPT `'comments'` нет в `supports`, это единственная правка бэкенда, которая может понадобиться (добавить `'comments'` в массив `supports`), причём вносить её сразу во все затронутые `register-*.php`, а не только там, где заметили при тестировании.

Комментарии в WP REST в принципе не требуют отдельного кастомного `rest-api.php` роута — используются штатные `/wp/v2/comments`:
- `GET /wp/v2/comments?post={id}&status=approve&order=asc` — список одобренных комментариев к посту, публично доступен по умолчанию.
- `POST /wp/v2/comments` с телом `{ post, author_name, author_email, content, parent? }` — создание. Публичная (неавторизованная) отправка комментария в WP REST по умолчанию разрешена, если в **Настройки → Обсуждение** не включено «Пользователи должны быть зарегистрированы и авторизованы» (`comment_registration`). **Перед реализацией фронтенда проверить этот флаг живым запросом** (`curl -X POST` тестовым телом к `testsite.vyatgeo.ru/wp-json/wp/v2/comments`), а не предполагать — если гостевые комментарии на сервере запрещены глобальной настройкой, об этом нужно сообщить, а не тихо превращать фронтенд в форму, которая всегда будет получать 401.

### 3.2. Composable

`src/composables/useComments.js`, без module-level singleton (комментарии не нужно переживать между переходами так же, как каталожное состояние — при возврате на страницу объекта их достаточно перезапросить):

```js
export function useComments() {
  const comments = ref([])
  const loading = ref(false)
  const error = ref(null)
  const submitting = ref(false)
  const submitError = ref(null)
  const submitted = ref(false)

  async function fetchComments(postId) { /* GET /wp/v2/comments?post=... */ }
  async function postComment(postId, { authorName, authorEmail, content, parent = null }) { /* POST /wp/v2/comments */ }

  return { comments, loading, error, submitting, submitError, submitted, fetchComments, postComment }
}
```

- `postComment` не бросает исключение — ошибка в `submitError.value` (различать как минимум: `closed` — комментарии выключены у записи, `forbidden` — гостевые комментарии запрещены сервером/настройкой, `network` — прочее), компонент показывает соответствующий текст.
- После успешной отправки (HTTP 201) **не** пытаться разобрать поле `status`/`comment_approved` из ответа, чтобы решить, одобрен ли комментарий сразу — анонимный запрос не получает это поле в REST-ответе (WP отдаёт его только при наличии capability на модерацию). Показывать одинаковое сообщение всегда: «Комментарий отправлен и появится после проверки модератором» — это стандартное поведение публичных WP-сайтов, не приближение к идеалу через угадывание статуса.

### 3.3. Компонент

`src/components/CommentsSection.vue` — единый переиспользуемый компонент (props: `postId`, `commentStatus`):

- Если `commentStatus !== 'open'` — компонент вообще не рендерит форму отправки; список существующих одобренных комментариев (если они есть) показывать в любом случае — закрытие комментариев останавливает только приём новых, не скрывает старые (это поведение самого `comment_status` в WP — если нужно другое, уточнять у пользователя, а не решать самостоятельно).
- Список: автор, дата, `content.rendered` (уже безопасный HTML от WP, но обернуть через `sanitize`-подход, консистентный с остальным контентом проекта — не выводить `v-html` без предварительной обработки, которая уже применяется к другим HTML-полям в проекте).
- Форма: имя, email, текст — `min-height: 44px` на полях (WCAG touch target, как у остальных интерактивных элементов, см. `CLAUDE.md`), стиль полей — тот же `.search-box`-паттерн (сплошная рамка 1.5px, radius, ochre-обводка по фокусу), что и у `AttractionControls.vue`, не новый стиль инпута.
- Вложенные ответы (`parent`) — не реализовывать в этой задаче, если явно не попросили: это отдельная функциональность (threading), избыточная для «базового функционала».

### 3.4. Подключение к существующим объектным страницам

Добавить `<CommentsSection :post-id="..." :comment-status="...">` в конец существующих `*ItemView.vue`/`*ObjectView.vue`, которые уже используют реальный REST API (после блока «похожие/ближайшие», см. структуру объектной страницы в `CLAUDE.md`):

- `ArchitectureObjectView.vue` (attraction)
- `EthnographyItemView.vue` (finding)
- `CityEventView.vue` (history)
- новые `PageView.vue` и `NewsItemView.vue` (см. §1–2)

`comment_status` для attraction/finding/history сейчас **не отдаётся** в кастомных bulk-эндпоинтах (`/objects`, они намеренно облегчены) — брать его из уже существующего детального запроса `/wp/v2/{cpt}/{id}?_embed=1`, который каждая из этих страниц и так делает, просто прокинуть поле `comment_status` из ответа в состояние компонента, если его там ещё нет.

**Не трогать** `NatureView.vue`/`NatureSiteView.vue`, `VictoryFacesView.vue`/`VictoryPersonView.vue`, `ArcheologyView.vue`/`ArcheologySiteView.vue` — они всё ещё на статичных моках (см. `CLAUDE.md`, раздел про интеграцию модулей), комментарии к моковым данным не имеют смысла.

## 4. Меню — интеграция с WordPress через собственный REST-роут

Публикация меню core-эндпоинтами WP (`/wp/v2/menus`, `/wp/v2/menu-items`) по умолчанию требует capability `edit_theme_options` — не публичны без дополнительной правки прав. Готовые сторонние плагины (`wp-api-menus` и т.п.) не используются — проект принципиально не тянет внешние зависимости для функциональности, которую можно реализовать несколькими десятками строк в уже существующей архитектуре (все остальные кастомные REST-роуты в проекте — свой код в `api/*/rest-api.php`, тот же принцип применяется и здесь).

### 4.1. Бэкенд

В `wp-theme/naslediye-vyatki-theme/functions.php`:

1. `register_nav_menus(['spa_primary' => 'Главное меню SPA'])` — регистрирует место меню, доступное в **Внешний вид → Меню** для назначения.
2. Новый REST-роут, неймспейс `nv/v1` (или отдельный небольшой файл `wp-theme/naslediye-vyatki-theme/menu-api.php`, подключаемый из `functions.php` — по аналогии с тем, как `admin/import.php` подключается отдельно):

```
GET nv/v1/menu/{location}
```

- `permission_callback => '__return_true'` (как у всех остальных кастомных роутов в проекте).
- `wp_get_nav_menu_locations()[$location]` → `$menu_id`; если локация не назначена ни одному меню — вернуть `[]` (пустой массив, не 404 — фронтенд должен молча фолбэчить на захардкоженное меню, см. §4.2), это ожидаемое переходное состояние, пока редактор не создал меню в админке.
- `wp_get_nav_menu_items($menu_id)` → плоский список с `menu_item_parent`, конвертировать в дерево (плоский формат с `parentId` тоже приемлем, если фронту проще — решить на этапе реализации и задокументировать в `api/docs/`).
- Формат одного пункта:

```json
{ "id": 12, "title": "Новости", "url": "/news", "parentId": 0, "order": 3, "target": "" }
```

- `url` — **не** абсолютный WP-URL пункта меню как есть. Редакторы создают пункты как «Произвольные ссылки» (custom link) в **Внешний вид → Меню**, вводя туда путь именно SPA-роутинга (`/news`, `/page/kontakty`, `/architecture`), а не URL WordPress permalink. Роут отдаёт `url` как есть (после `wp_strip_all_tags`), без попыток резолвить `object_id`/`post_type` пункта меню в SPA-путь — это осознанное упрощение (см. §4.3, почему не автоматический резолвинг).
- Задокументировать эндпоинт в `api/docs/` (новый файл `api/docs/menu.md`), по образцу структуры остальных файлов в этой папке.

### 4.2. Фронтенд

- `src/composables/useMenu.js`: `useMenu()` → `{ items, loading, error, fetchMenu(location) }`, тот же паттерн no-throw, что и везде.
- В `SiteHeader.vue`: при монтировании — `fetchMenu('spa_primary')`. Если ответ непустой — использовать пункты из WP (сконвертировать плоский список в дерево для вложенных пунктов, если такие появятся; для текущей плоской навигации достаточно списка верхнего уровня, `parentId === 0`). **Если ответ пустой или запрос упал** — оставить текущий захардкоженный `navItems` как фолбэк, не показывать пустое меню. Это переходный период: пока редактор не наполнил меню `spa_primary` в WP-админке, сайт продолжает работать как сейчас.
- Активный пункт (`active`, уже принимается как prop) — сравнение `to.path` с `url` пришедшего пункта, а не жёстко заданный ключ, если меню пришло из API (ключевое отличие от текущей реализации, где `active` — литеральная строка, сверяемая с массивом из 8 фиксированных ключей).
- Для внешних ссылок (если редактор всё же вставит абсолютный URL стороннего сайта) — `<a>` вместо `<RouterLink>`, определять по `url.startsWith('http')` && не начинается с текущего домена/`SITE_URL`.

### 4.3. Почему не автоматический резолвинг WP permalink → SPA-путь

Альтернативный (более «умный») вариант — резолвить `object_id`/`type` пункта меню (если это ссылка на реальный `post`/`page`/`term`, а не custom link) через ту же логику, что уже есть в `router/index.js` для `/archives/{module}/{slug}` (см. `moduleToCpt`/`moduleToRoute` и `resolveSlugToId`). Это возможно и совместимо с существующим кодом, но добавляет неочевидную связь «тип WP-объекта → корневой SPA-роут модуля», которую придётся поддерживать вручную при каждом новом модуле, тогда как custom link с готовым SPA-путём редактор может создать сам без правок кода. **Использовать этот подход только если пользователь явно попросит** после того, как увидит ограничения простого варианта на практике — не реализовывать сразу оба.

## 5. Общие технические требования

- **Устранить дублирование `decodeEntities`/`resolveRelativeUrls`**, если задача требует их в четвёртом-пятом composable подряд (`usePage.js`, `usePosts.js`) — сейчас они продублированы по одной копии в `useAttractions.js`/`useFindings.js`/`useHistory.js`. Вынести в `src/composables/useHtmlContent.js` (или аналогичное общее имя) и импортировать из всех composables, включая уже существующие три модуля — **не оставлять пятую копию** того же кода. Это рефакторинг существующих файлов, не только новых — согласовать объём правки, если она кажется большой, но не размножать копию в шестой раз.
- Все новые composables — без исключений наружу, ошибка в `error.value`/`submitError.value`.
- Все цвета/отступы — через CSS-переменные (`var(--color-*)`, `var(--space-*)`), без хардкода. Курсив/малые начертания Playfair — не использовать для обычного текста комментариев/постов.
- `min-height: 44px` на полях формы комментариев и на новых интерактивных элементах меню.
- После правок в `.vue`-файлах — прогнать `node .claude/skills/impeccable/scripts/detect.mjs --json <изменённые .vue файлы>` и `npm run build`, прежде чем считать задачу завершённой (обязательное правило проекта, не опция).
- PHP-правки (`functions.php`, новый `menu-api.php`, возможные правки `supports` в `register-*.php`) — проверить `php -l`, затем живым `curl`-запросом к `testsite.vyatgeo.ru` **после** ручного переноса по FTP и подтверждения деплоя от пользователя (правки в `api/`/`wp-theme/` в этом репозитории не применяются на сервере автоматически).

## 6. Порядок реализации и проверка

1. Бэкенд: проверить/добавить `'comments'` в `supports` нужных CPT, если отсутствует; добавить `register_nav_menus` + `nv/v1/menu/{location}` в тему; задокументировать в `api/docs/menu.md`.
2. Дождаться переноса на `testsite.vyatgeo.ru` и подтверждения деплоя.
3. Проверить эндпоинты живыми запросами:
   ```bash
   curl -s "https://testsite.vyatgeo.ru/wp-json/wp/v2/pages?per_page=1" | jq '.[0] | {id, slug, title}'
   curl -s "https://testsite.vyatgeo.ru/wp-json/wp/v2/posts?per_page=1" | jq '.[0] | {id, title}'
   curl -s "https://testsite.vyatgeo.ru/wp-json/wp/v2/attraction/1" | jq '.comment_status'
   curl -s "https://testsite.vyatgeo.ru/wp-json/wp/v2/comments?post=1" | jq 'length'
   curl -sX POST "https://testsite.vyatgeo.ru/wp-json/wp/v2/comments" -H 'Content-Type: application/json' \
     -d '{"post":1,"author_name":"Тест","author_email":"test@example.com","content":"Тестовый комментарий"}' | jq '.'
   curl -s "https://testsite.vyatgeo.ru/wp-json/nv/v1/menu/spa_primary" | jq '.'
   ```
4. Фронтенд: composables → views/компоненты → роуты → подключение `CommentsSection` в существующие страницы → замена `navItems` в `SiteHeader.vue` на данные из `useMenu`.
