# Плагин «Геобаза археологических изысканий» (geopoints)

Файлы: `api/geopoints/` — `geopoints.php`, `activation.php`, `register-geopoints.php`, `rest-api.php`, `taxonomy-widget.php`, `js/`, `templates/`, `vue/`.

Самый большой и самый сложный из четырёх плагинов: 4 таксономии, два параллельных поколения REST API (v1/v2) и собственный Vue SPA (Vue-CLI/Webpack-сборка — `vue/js/app.js` + `chunk-vendors.js`, ~510 КБ суммарно).

## Назначение

Карта археологических «Работ» (раскопок/изысканий) с фильтрами по руководителю, типу работ, глубине и периоду.

## Зависимость

Как и `attraction`, требует активный плагин **Yamaps** — предупреждение в админке, если он выключен (`activation.php:15-28`). В `register-geopoints.php:640` дополнительно жёстко зашит **API-ключ Яндекс.Карт** (`ba0d0589-f903-43e9-b3d3-cc290988b69a`), подключаемый напрямую в метабоксе редактирования координат — виден в исходном коде страницы админки любому, у кого есть доступ к `wp-admin`.

## Регистрируемые сущности

- **CPT `geopoints`** («Работы») — `show_in_rest: true`, `supports: title, editor, comments, revisions, thumbnail`, архив включён.
- **Мета-поля** через `register_rest_field`: `address`, `area`, `begin_time`, `end_time`, `geopoints_coord` (строка `"lat, lng"`), `geopoints_pages` (массив ID связанных обычных постов блога), `imgSrc`.
- **4 кастомные таксономии**, все со своими цветовыми term-meta полями и REST-полями:
  - `headman` (Руководитель) — не иерархическая, term-meta `headman-color` + `headman-image-id` (с медиатекой в форме термина и шорткодом `[headman_photo]`, `register-geopoints.php:255-286`)
  - `deep` (Глубина) — не иерархическая, term-meta `deep-color`
  - `worktype` (Тип работ) — не иерархическая, term-meta `worktype-color`
  - `workdate` (Период работ) — **иерархическая**, term-meta `workdate-start`/`workdate-stop`/`workdate-npp` (порядок сортировки)

Term `workdate` для конкретной работы вычисляется **автоматически** при сохранении поста: PHP берёт все зарегистрированные периоды, сравнивает их границы с `begin_time`/`end_time` работы и подставляет пересекающиеся периоды как термины (`register-geopoints.php:796-821`) — то есть это не ручной выбор в UI, а side-effect логики `save_post`.

## REST API — два параллельных поколения

Оба набора endpoint'ов зарегистрированы и живы одновременно на сервере (подтверждено через `/wp-json/` discovery: `geopoints/v1` и `geopoints/v2` присутствуют оба).

| Namespace | Роут | Что делает |
|---|---|---|
| v1 и v2 | `GET /points` | Все точки карты |
| v1 и v2 | `GET /workdate`, `/worktype`, `/deep`, `/headman` | Списки терминов таксономий |
| v1 и v2 | `GET /posts`, `/posts/{id}` | Обычные посты блога (не CPT geopoints!) |
| v1 и v2 | `GET /cats/`, `/cats/{id}` | Категории блога + связанные посты/подкатегории |

**v1** реализован как обёртка поверх штатного REST через внутренний `rest_do_request()` (напр. `new WP_REST_Request('GET', '/wp/v2/workdate')`) — то есть каждый вызов v1 внутри делает ещё один внутренний REST-запрос и переформатирует его ответ. `GET /v1/points` отдаёт GeoJSON-подобную структуру (`type: Feature`, `geometry.coordinates`, `properties.balloonContentHeader` и т.д. — заточено под прямую передачу в Yandex Maps API).

**v2** переписан без внутренних REST-вызовов — прямые запросы к `$wpdb`/`get_terms`/`get_posts` с предзагрузкой meta-кэша (`update_meta_cache`, `rest-api.php:146-148`) — заметно менее затратный. `GET /v2/points` отдаёт плоские объекты без GeoJSON-обёртки, но с дополнительным полем `img` (ID вложения featured image, которого нет в v1).

**Важное наблюдение**: собранный Vue-бандл плагина (`vue/js/app.js`) обращается **только к v1**-эндпоинтам (`geopoints/v1/points`, `/cats`, `/deep`, `/headman`, `/posts`, `/workdate`, `/worktype`) — v2 присутствует и работает на сервере, но не используется ни одним известным клиентом. Похоже на подготовку под будущую миграцию (возможно, именно под naslediye-vyatki).

Пример живого ответа `GET /geopoints/v2/points` (обрезано):
```json
[{
  "id": 11262,
  "coordinates": [58.5615106388889, 49.6369253055556],
  "title": "Слобода Куроческины, Д.5,7,11,13а,...",
  "place": "Слобода Куроческины, ...",
  "imgSrc": "https://.../image_11262-4-150x150.png",
  "img": 13925,
  "manager": 149,
  "depth": 171,
  "type": "hole",
  "date": 2022,

```

## `/posts`, `/cats` — отдельная генерическая часть API

Эти маршруты не относятся к CPT `geopoints` вообще — это обёртка над обычными постами блога и категориями, изначально нужная Vue SPA плагина, чтобы внутри попапа с точкой карты показывать список «связанных статей» (`geopoints_pages` мета-поле хранит ID таких постов, `rest-api.php:60-77` в v1-версии `/points` формирует HTML-ссылки на них вида `#/page/{id}`). Если naslediye-vyatki не планирует воспроизводить этот попап-механизм — эта часть API, скорее всего, не понадобится.

## `taxonomy-widget.php`

Не относится к REST API — классический WP-виджет (`WP_Widget`) для вывода списка терминов произвольной таксономии в сайдбаре темы. Изолирован от остального плагина, использует свой Walker для dropdown-режима. Упомянут для полноты картины, но фронтенд naslediye-vyatki с ним не взаимодействует.

## CORS

`geopoints.php:7` явно выставляет `header('Access-Control-Allow-Origin: *')` на каждом `init` — но, как показала проверка живого сервера, фактический ответ содержит **не `*`, а отражённый Origin запроса** (`Access-Control-Allow-Origin: http://localhost:5173`) — значит поверх этого явного заголовка ядро WP всё равно перезаписывает его своей логикой CORS (`rest_send_cors_headers`). Явный заголовок в коде плагина, по сути, избыточен для `/wp-json/*` запросов.

## Замечания для интеграции

- Для нового фронтенда логичнее ориентироваться на **v2** (меньше внутренних запросов на сервере, есть `img`), а не копировать v1 только потому что так делает старый Vue-виджет.
- GeoJSON-формат v1 нужен, только если планируется использовать тот же слой Яндекс.Карт API «из коробки» — если карта в naslediye-vyatki рисуется иначе (SVG/своя реализация, как в текущих `CatalogMap.vue`), v2 удобнее для трансформации в собственную модель данных.
- Хардкод API-ключа Яндекс.Карт в PHP — вопрос не для фронтенда, но стоит поднять отдельно с владельцем WP-сайта (ключ публично виден в HTML исходном коде страницы редактирования поста).
