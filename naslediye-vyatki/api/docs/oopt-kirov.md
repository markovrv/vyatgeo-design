# Плагин «Памятники природы Кировской области» (oopt-kirov)

Файлы: `api/oopt-kirov/` — `oopt-kirov.php`, `register-oopt.php`, `rest-api.php`, `js/adminMap.js`, `templates/single-oopt.php`. Разработан по образцу `attraction` (см. `api/prompt-geroi-oopt-plugins.md` — исходное ТЗ), без своего Vue/SPA-бандла — как и `geroi-vyatki`, каталог/карта реализуются во Vue-проекте, а не в плагине.

**Переименование**: изначально плагин назывался «ООПТ Кировской области» — по просьбе переименован в «Памятники природы Кировской области» (только заголовок/labels; slug `oopt-kirov`, CPT `oopt`, префикс мета-полей `oopt_*`, таксономии и REST-неймспейс `oopt/v1` не менялись).

## Назначение

Каталог особо охраняемых природных территорий (памятников природы) Кировской области. **Данные загружены** (17 записей, `Geroi.xlsx`, Лист2), фронтенд ещё не написан. Это **точное** соответствие моковому `NatureView.vue` — совпадает даже заголовок раздела («Памятники природы Кировской области», см. `CLAUDE.md`, статус-абзац).

## Регистрируемые сущности

- **CPT `oopt`** — `show_in_rest: true`, `supports: title, editor, thumbnail, post-thumbnails, comments, revisions`, архив включён, `menu_position: 17`.
- **3 таксономии**:
  - `oopt_district` (Район) — иерархическая, 7 терминов на живых данных (Арбажский, Афанасьевский, Богородский, Верхнекамский, Вятско-Полянский, Даровской, Зуевский)
  - `oopt_profile` (Профиль) — иерархическая, 3 термина (Гидрологический, Ботанический, Геологический)
  - `oopt_species` (Охраняемые виды) — **неиерархическая**, 28 терминов на живых данных. Название термина — только видовое название («Кувшинка чисто-белая»); охранный статус, который в источнике идёт в скобках («Приложение 2 КККО», «III КККО» и т.п.), **не входит в название** — хранится отдельным term meta `oopt_species_status` (`register_term_meta`, см. ниже).
- **Мета-поля** через `register_rest_field`: `oopt_coord` (строка `"lat, lng"`), `oopt_area` (число, га), `oopt_summary` (краткое описание — то же значение отдаётся в `/objects` как `summarize`), `oopt_imgSrc`, `oopt_color`.

Gutenberg отключён для `oopt`.

### `oopt_species_status` — term meta с явным embed-контекстом

```php
register_term_meta('oopt_species', 'oopt_species_status', [
    'type' => 'string',
    'single' => true,
    'show_in_rest' => [
        'schema' => ['type' => 'string', 'context' => ['view', 'edit', 'embed']],
    ],
    'sanitize_callback' => 'sanitize_text_field',
]);
```

**Важный нюанс, пойманный на живых данных**: короткая форма `'show_in_rest' => true` добавляет term meta только в контексты `view`/`edit` — в `_embedded['wp:term']` (при `?_embed=1`) поле **не попадает**, несмотря на `show_in_rest: true`. Проверено эмпирически: `/wp/v2/oopt/{id}?_embed=1` отдавал термины вида без `meta` вовсе, хотя прямой запрос `/wp/v2/oopt_species/{term_id}` показывал значение корректно. Нужно явно перечислить `context` в `schema`, включая `embed` — только тогда статус вида приходит вместе с постом одним запросом, без дополнительного batch-запроса к `/wp/v2/oopt_species` на каждый вид.

Редактирование `oopt_species_status` в админке — не на странице записи (там стандартный WP tags-бокс для назначения видов посту), а на экране самого термина (`oopt_species_add_form_fields`/`edit_form_fields`, хуки `created_oopt_species`/`edited_oopt_species`).

## Админ-панель

Два метабокса: «Аннотация» (`oopt_summary`, textarea) и «Карта и параметры» (карта Yandex, `id="oopt_coord-input"`, + `oopt_area`/`oopt_imgSrc`/`oopt_color`). Таксономии (`oopt_district`/`oopt_profile`/`oopt_species`) назначаются стандартными блоками WP для соответствующего типа таксономии (чекбоксы для иерархических, tags-инпут для `oopt_species`), отдельного UI под них не писалось.

## REST API

| Метод | Роут | Доступ | Назначение |
|---|---|---|---|
| GET | `/oopt/v1/objects` | публичный | Все опубликованные памятники природы, без пагинации |
| GET | `/oopt/v1/objects/{id}/adjacent` | публичный | Предыдущий/следующий по возрастанию ID |
| GET | `/oopt/v1/objects/{id}/nearby?max_distance={km}` | публичный | До 4 ближайших по координатам в радиусе `max_distance` км (гаверсинус) |

Пример живого ответа `GET /oopt/v1/objects` (один элемент из 17):
```json
{
  "id": 22932,
  "coordinates": [58.658429, 49.712168],
  "title": "Большой Кирсинский пруд",
  "place": "Верхнекамский",
  "imgSrc": "https://testsite.vyatgeo.ru/wp-content/uploads/2026/08/placeholder-150x150.jpg",
  "color": "#3C7A8C",
  "summarize": "Искусственный пруд площадью зеркала 433 га, часть водной системы, соединяющей Вятку и Каму. Сосновые, еловые и смешанные леса по берегам, сплавина с клюквой и багульником.",
  "content": "",
  "img": 22710
}
```

`place` — название района (`oopt_district`), а не свободный текст: у `oopt` в источнике нет отдельного текстового поля «место». Как и у `hero` (и в отличие от `attraction`), **`summarize` заполнен** значением `oopt_summary` уже в bulk-ответе — так задумано контрактом, аннотация нужна сразу в каталоге/на карте. `content` — единственное тяжёлое поле, всегда пустая строка, полный текст — через `/wp/v2/oopt/{id}?_embed=1`.

Площадь, охраняемые виды (с их `oopt_species_status`), профиль — только в детальном запросе `/wp/v2/oopt/{id}?_embed=1`, в bulk `/objects` не выводятся. Пример терминов на живой записи `id=22932`: `oopt_district: Верхнекамский`, `oopt_profile: Гидрологический`, `oopt_species: Кувшинка четырехгранная / Кувшинка чисто-белая / серая цапля / Шмель окаймленный` (у части — заполненный `oopt_species_status`, у части — пустой: в источнике не у всех видов был указан статус в скобках).

`/adjacent`, `/nearby` — тот же формат `navItem`, что у `attraction`/`hero`.

## REST-запросы на запись и очистка полей

Тот же паттерн, что и у `geroi-vyatki` (см. `CLAUDE.md`, «REST-паттерны на бэкенде», и `api/docs/geroi-vyatki.md`): `save_post` выходит раньше при `REST_REQUEST`, `update_callback` пишет `$value ?? ''` вместо игнорирования пустых значений. У `oopt` это дополнительно распространяется на term-meta хуки `created_oopt_species`/`edited_oopt_species` (у `edited_oopt_species` была деструктивная `else`-ветка с `delete_term_meta` — без гварда REST-переименование вида стирало бы его `oopt_species_status`). Проверено живым CRUD-тестом.

## Импорт (`api/import_geroi_oopt.py`)

Тот же скрипт, что и для героев (см. `api/docs/geroi-vyatki.md`), функция `import_oopt`/`build_oopt_payload`:

- **Координаты отсутствуют у всех 17 строк источника** — все получили случайную точку в границах Кирова.
- **Фото отсутствует у всех 17 строк** — тот же переиспользуемый плейсхолдер, что и у героев.
- `parse_species()` разбирает `Охраняемые виды` по `,`, регуляркой `^(.*?)\s*\(([^)]+)\)\s*$` выделяет статус из скобок; значение-заглушка «Редких видов не выявлено» (означает отсутствие видов, а не название) при импорте пропускается, термином не становится.
- 8 из 17 строк хранят «Литературное описание» как `{название} - {краткое описание};{настоящий текст}` — `clean_literary_description()` берёт то, что после первой `;`.
- Термины `oopt_species` создаются атомарно вместе с постом (`meta: {oopt_species_status: ...}` в теле запроса создания термина) — так же, как и у поста, без последующего PATCH.
- Запуск: `python import_geroi_oopt.py --only oopt [--limit N] [--dry-run]`.

## Замечания для интеграции

- Строить `NatureView.vue`/`NatureItemView.vue` (существующий мок уже так называется) и `useOopt.js` по паттерну `useAttractions.js` — тот же контракт `/objects`, `/adjacent`, `/nearby`.
- `oopt_species` на карточке/странице объекта — список чипов «Название (статус)», статус показывать только если `oopt_species_status` не пустой (см. `templates/single-oopt.php` для готового примера сборки такой строки на PHP-стороне).
- Для батч-получения `oopt_species_status` нескольких видов сразу (если понадобится где-то кроме страницы одного объекта) — обычный `/wp/v2/oopt_species?include=id1,id2,...`, а не N отдельных запросов; embed-контекст термина внутри `/wp/v2/oopt/{id}?_embed=1` уже содержит статус благодаря явному `context` в schema (см. выше) — для одиночного объекта отдельный запрос не нужен вообще.
