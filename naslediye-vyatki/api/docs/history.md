# Плагин «История города Хлынова/Вятки/Кирова: Люди и даты» (history)

Файлы: `api/history/` — единственный `history.php` (540 строк, весь функционал в одном файле) + два бандла `vue/` и `spa/`.

## Назначение

Лента исторических дат/событий города с фильтрацией по периоду. Единственный из 4 плагинов, где **read-API не единственный способ фильтрации** — есть ещё серверная фильтрация архива через cookie + `pre_get_posts`, работающая параллельно с REST-эндпоинтом.

## Регистрируемые сущности

- **CPT `history`** («Даты») — `show_in_rest: true`, `supports: title, editor, comments, revisions, thumbnail`, без своих таксономий, архив включён.
- **Мета-поля** через `register_rest_field` (`history.php:135-156`):
  - `history_date_value` — дата в формате `Y-m-d` (используется для сортировки/фильтра, ввод как `<input type="date">`)
  - `history_date_text` — отображаемый текст даты (например, «1374 год», произвольная строка, не обязательно валидная дата)

Gutenberg отключён для `history` (`history.php:160-164`).

## Два независимых фронтенда в одном плагине

1. **`vue/`** — небольшой Vue-бандл, подключается только на архивной странице CPT (`is_archive()`, `history.php:81-82`) и монтируется внутрь hero-секции темы (`blocksy:hero:after`, `history.php:341-346`, `<div id="app">`). Судя по коду вокруг — вероятно, интерактивные кнопки быстрого выбора периода (14-17 века / 18 век / ... / 21 век), которые в PHP-версии реализованы как обычные `onclick="setperiod(...)"` (`history.php:493-497`), пишущие в cookies и делающие обычный GET-сабмит формы. Сама фильтрация архива в этом сценарии идёт **не через REST**, а через WP `pre_get_posts` + `meta_query` по `history_date_value`, управляемый GET-параметрами `sort_order`/`start_date`/`end_date`, которые сохраняются в cookie на год (`history.php:214-253`, `setCookie(...; secure; SameSite=Strict)`).
2. **`spa/`** — полноценное отдельное SPA (судя по файлам `primeicons-*.woff/eot/svg` — построено на **PrimeVue**), подключается на отдельной статической странице `history-spa`, созданной при активации плагина (`history.php:22-75`). Хост-страница инициализирует SPA через глобальные переменные перед монтированием:
   ```html
   <script>
     window.apiUrl = "../../";   // относительный путь к корню REST API
     window.theme = "white";
     window.primary = 10;
     window.surface = 3;
     ...
   </script>
   <div id="app"></div>
   ```
   Это явно спроектированный «конфигурируемый» встраиваемый виджет — параметры темы/цвета передаются извне через глобальные переменные окна перед загрузкой скрипта, а не зашиты в бандл.

## REST API

Плагин **не регистрирует собственный namespace `history/v1`** — только один кастомный роут в общем неймспейсе `custom/v1` (используется совместно, возможно, с другими интеграциями сайта):

| Метод | Роут | Доступ | Назначение |
|---|---|---|---|
| GET | `/custom/v1/history/` | публичный | Список дат с фильтром по диапазону + пагинация |

Параметры: `start`, `stop` (валидируются `isValidDate()` — строго `Y-m-d`, иначе игнорируются), `order` (`ASC`/`DESC`, по умолчанию `ASC`), `page`, `per_page` (по умолч. 10). Ответ:
```json
{
  "posts": [
    { "id": 6033, "title": "Первое упоминание города Вятки в русской летописи", "content": "<center>...</center>", "history_date_text": "1374 год", "history_date_value": "1374-01-01" }
  ],
  "pagination": { "total_posts": 87, "total_pages": 9, "current_page": 1, "posts_per_page": 10 }
}
```
Проверено на живом сервере — реальные записи с HTML-контентом внутри `content` (включает `<img>`-теги с относительными путями `../../wp-content/uploads/...`, рассчитанными на то, что рендерящая страница лежит на 2 уровня глубже корня сайта).

Записи для write-операций нет вообще — это единственный из 4 плагинов, где REST-слой строго read-only; всё редактирование — через `wp-admin` (метабокс `history_meta_box`, `history.php:178-189`).

## CORS

Явного заголовка нет; проверка живого сервера подтвердила стандартное для всех эндпоинтов сайта поведение — WP-ядро отражает `Origin` запроса и разрешает credentials.

## Замечания для интеграции

- Относительные пути в HTML внутри `content` (`../../wp-content/...`) — это наследие того, что контент изначально рендерился на конкретной глубине URL внутри WP-темы. При выводе этого HTML в Vue-компоненте naslediye-vyatki (например, через `v-html`) пути **сломаются**, если страница не находится ровно на той же глубине — потребуется либо переписывать относительные пути в абсолютные на фронте (заменой префикса на `https://testsite.vyatgeo.ru/`), либо просить бэкенд отдавать абсолютные URL.
- `history_date_text` — это не отформатированная `history_date_value`, а независимое ручное поле; при сортировке используйте `history_date_value`, а `history_date_text` — только для отображения (в БД возможны исторически «нестрогие» тексты вроде «конец XIV века», не парсящиеся как дата).
- Два хостовых механизма (`vue/` на архиве и `spa/` на отдельной странице) решают одну и ту же задачу («лента дат с фильтром по периоду») по-разному: первый полагается на серверный `pre_get_posts` + cookies, второй — на чистый REST через `custom/v1/history`. Для naslediye-vyatki актуален только второй паттерн (чистый REST, без серверного рендера и cookies) — именно `GET /custom/v1/history/` стоит использовать как источник данных для `HistoricCitiesView`/аналогичных разделов.
