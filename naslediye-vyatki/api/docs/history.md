# Плагин «История города Хлынова/Вятки/Кирова: Люди и даты» (history)

Файлы: `api/history/` — единственный `history.php` (540 строк, весь функционал в одном файле) + два бандла `vue/` и `spa/`.

## Назначение

Лента исторических дат/событий города с фильтрацией по периоду. Единственный из 4 плагинов, где **read-API не единственный способ фильтрации** — есть ещё серверная фильтрация архива через cookie + `pre_get_posts`, работающая параллельно с REST-эндпоинтом.

## Регистрируемые сущности

- **CPT `history`** («Даты») — `show_in_rest: true`, `supports: title, editor, comments, revisions, thumbnail`, архив включён. Одна таксономия — `city` (см. ниже).
- **Мета-поля** через `register_rest_field` (`history.php:135-156`):
  - `history_date_value` — дата в формате `Y-m-d` (используется для сортировки/фильтра, ввод как `<input type="date">`)
  - `history_date_text` — отображаемый текст даты (например, «1374 год», произвольная строка, не обязательно валидная дата)

Gutenberg отключён для `history` (`history.php:160-164`).

## Таксономия `city` (модуль «Города», добавлено для naslediye-vyatki)

Каждая запись «Даты» относится ровно к одному городу — hierarchical-таксономия (checkbox-список в редакторе, а не свободный tag-инпут). Ленты времени на фронте выводятся строго по городам (`GET history/v1/events?city={slug}`); в фильтрах каталога таксономия не участвует — выбор города происходит через отдельную страницу выбора (`HistoricCitiesView.vue`), а не через чипы фильтра.

Term meta (`register_term_meta`, `show_in_rest: true`):
- `city_short` (string) — краткая характеристика для карточки города на странице выбора города
- `city_photo` (int, ID вложения) — фото города; у терминов нет нативной миниатюры, поэтому свой media-picker на `wp.media` на экранах добавления/редактирования термина (хуки `city_add_form_fields`/`city_edit_form_fields`)
- `city_coord` (string, `"lat, lng"`) — координаты для пина на карте городов (`HistoricCitiesView.vue`, режим «На карте», компонент `HistoryCitiesMap.vue`). Тот же формат и тот же классический Yandex Maps JS API v2.1, что и у `attraction_coord`/`geopoints_coord` (`api/attraction/js/adminMap.js`, `api/geopoints/js/adminMap.js`) — своя копия `api/history/js/adminCityMap.js`, мини-карта 300px в обоих экранах (клик по карте или ручной ввод в поле обновляют друг друга). `history/v1/cities` отдаёт распарсенное значение как `coordinates: [lat, lng]` или `null`, если не заполнено/невалидно.

Плюс встроенное поле WP «Описание» термина — используется как полное описание города.

Засеяны 7 терминов проекта (`kirov`, `kotelnich`, `orlov`, `slobodskoy`, `yaransk`, `malmyzh`, `urzhum`) одноразовым сидингом на `init` (флаг `history_city_seeded` в опциях защищает от повтора); на момент внедрения все существующие записи `history` были привязаны к `kirov` — у остальных 6 городов `eventsCount === 0`, наполнение будет вручную через админку.

## Два независимых фронтенда в одном плагине

1. **`vue/`** — небольшой Vue-бандл, подключается только на архивной странице CPT (`is_archive()`, `history.php:81-82`) и монтируется внутрь hero-секции темы (`blocksy:hero:after`, `history.php:341-346`, `<div id="app">`). Судя по коду вокруг — вероятно, интерактивные кнопки быстрого выбора периода (14-17 века / 18 век / ... / 21 век), которые в PHP-версии реализованы как обычные `onclick="setperiod(...)"` (`history.php:493-497`), пишущие в cookies и делающие обычный GET-сабмит формы. Сама фильтрация архива в этом сценарии идёт **не через REST**, а через WP `pre_get_posts` + `meta_query` по `history_date_value`, управляемый GET-параметрами `sort_order`/`start_date`/`end_date`, которые сохраняются в cookie на год (`history.php:214-253`, `setCookie(...; secure; SameSite=Strict)`).
2. **`spa/`** — полноценное отдельное SPA (судя по файлам `primeicons-*.woff/eot/svg` — построено на **PrimeVue**), подключается на отдельной статической странице `history-spa`, созданной при активации плагина (`history.php:22-75`). Хост-страница инициализирует SPA через глобальные переменные перед монтированием:
   ```html
   <script>
     window.apiUrl = "../../";   // относительный путь к корню REST API
     window.theme = "white";
     window.primary = 10;
     window.surface = 3;
     ...
   </script>
   <div id="app"></div>
   ```
   Это явно спроектированный «конфигурируемый» встраиваемый виджет — параметры темы/цвета передаются извне через глобальные переменные окна перед загрузкой скрипта, а не зашиты в бандл.

## REST API

Помимо legacy-роута в общем неймспейсе `custom/v1` (см. ниже), плагин регистрирует свой namespace `history/v1` — по конвенции `attraction/v1`/`findings/v1` (см. `CLAUDE.md`, «Паттерны модулей с реальным API»), это актуальный источник данных для naslediye-vyatki:

| Метод | Роут | Доступ | Назначение |
|---|---|---|---|
| GET | `/history/v1/cities` | публичный | Все 7 городов: slug, name, description, short, photo, photoThumb, coordinates, eventsCount |
| GET | `/history/v1/events?city={slug}&page&per_page&century&search` | публичный | Постранично (по умолч. `per_page=10`) события города, отсортированы по `history_date_value` ASC + вторичная сортировка по ID (тай-брейк при совпадающих датах — таких десятки); `city` обязателен, 404 если город не найден |
| GET | `/history/v1/events/{id}/adjacent` | публичный | Предыдущее/следующее событие по дате **в рамках того же города** |
| GET | `/history/v1/events/{id}/nearby` | публичный | Окно до 5 событий (2 до, текущее, 2 после) по дате в рамках того же города — для мини-ленты навигации на странице события |

`/history/v1/cities`: `photo` — фото в максимальном доступном качестве (`full → large → medium_large → medium`, приоритет **обратный** обычной цепочке для карточек — здесь фото используется и на маленькой карточке города, и на полноэкранном hero ленты времени, поэтому берём самое крупное, что есть); `photoThumb` — отдельно, миниатюра 150×150 для пина на карте (`HistoryCitiesMap.vue`) — крупное фото не нужно и не помещается в круглый пин; `coordinates` — `[lat, lng]` из `city_coord` или `null`, если не заполнено/невалидно.

`/history/v1/events` — по 10 записей за раз (у Кирова 666+ событий, отдавать всё разом смысла нет: карте тут делать нечего, лента рендерится строго последовательно). Параметры сверх `city`:
- `page`, `per_page` — стандартная пагинация, ответ включает `pagination: { page, perPage, total, totalPages }`;
- `century` — одно из `14-17` / `18` / `19` / `20` / `21` (соответствует `history_century_range()` на сервере — `1300-1699`/`1700-1799`/.../`2000-2099` по `history_date_value` через `meta_query BETWEEN`); без параметра или с любым другим значением — без фильтра;
- `search` — стандартный WP-поиск (`$args['s']`, ищет по названию и тексту события), тот же паттерн, что и `search` в `findings/v1/findings`.

Форма ответа — `{ "events": [...], "pagination": {...} }`, а не плоский массив (изменилось при добавлении пагинации — до этого `/events` отдавал всё разом плоским списком).

Деталь одного события фронт получает не отсюда, а напрямую штатным `GET /wp/v2/history/{id}?_embed=1` (как `useAttraction` ходит в `/wp/v2/attraction/{id}`) — `history_date_text`/`history_date_value` уже отданы через `register_rest_field`, город — через `_embedded['wp:term']` (единственная таксономия на CPT).

Bulk-список `/events` отдаёт только миниатюру 150×150 (`imgSrc`) + ID вложения (`img`) — апгрейд качества делает фронт батч-запросом к `/wp/v2/media?include=...&_fields=id,media_details` с полной цепочкой фолбэка `medium_large → large → medium → full` (см. `useHistoryThumbnails`, тот же паттерн, что и в Архитектуре/Этнографии — сокращать цепочку до `medium_large → large → null` нельзя, часть фото не имеет ни того ни другого, если оригинал меньше их порога). Разрешённые URL кэшируются на фронте и в `sessionStorage` (см. `CLAUDE.md`) — при возврате на ленту после просмотра события повторный батч-запрос не нужен.

### Legacy: `custom/v1/history` (не используется во Vue-фронте)

| Метод | Роут | Доступ | Назначение |
|---|---|---|---|
| GET | `/custom/v1/history/` | публичный | Список дат с фильтром по диапазону + пагинация |

Параметры: `start`, `stop` (валидируются `isValidDate()` — строго `Y-m-d`, иначе игнорируются), `order` (`ASC`/`DESC`, по умолчанию `ASC`), `page`, `per_page` (по умолч. 10). Ответ:
```json
{
  "posts": [
    { "id": 6033, "title": "Первое упоминание города Вятки в русской летописи", "content": "<center>...</center>", "history_date_text": "1374 год", "history_date_value": "1374-01-01" }
  ],
  "pagination": { "total_posts": 87, "total_pages": 9, "current_page": 1, "posts_per_page": 10 }
}
```
Проверено на живом сервере — реальные записи с HTML-контентом внутри `content` (включает `<img>`-теги с относительными путями `../../wp-content/uploads/...`, рассчитанными на то, что рендерящая страница лежит на 2 уровня глубже корня сайта).

Записи для write-операций нет вообще — это единственный из 4 плагинов, где REST-слой строго read-only; всё редактирование — через `wp-admin` (метабокс `history_meta_box`, `history.php:178-189`).

## CORS

Явного заголовка нет; проверка живого сервера подтвердила стандартное для всех эндпоинтов сайта поведение — WP-ядро отражает `Origin` запроса и разрешает credentials.

## Замечания для интеграции

- Относительные пути в HTML внутри `content` (`../../wp-content/...`) — это наследие того, что контент изначально рендерился на конкретной глубине URL внутри WP-темы. При выводе этого HTML в Vue-компоненте naslediye-vyatki (например, через `v-html`) пути **сломаются**, если страница не находится ровно на той же глубине — потребуется либо переписывать относительные пути в абсолютные на фронте (заменой префикса на `https://testsite.vyatgeo.ru/`), либо просить бэкенд отдавать абсолютные URL.
- `history_date_text` — это не отформатированная `history_date_value`, а независимое ручное поле; при сортировке используйте `history_date_value`, а `history_date_text` — только для отображения (в БД возможны исторически «нестрогие» тексты вроде «конец XIV века», не парсящиеся как дата).
- Два хостовых механизма (`vue/` на архиве и `spa/` на отдельной странице) и legacy `custom/v1/history` — наследие старой (не Vue) реализации раздела, для naslediye-vyatki не используются вообще. Актуальный источник данных для `HistoricCitiesView`/`CityTimelineView`/`CityEventView` — новый неймспейс `history/v1/*` (список городов, события по городу, adjacent/nearby по датам) плюс штатный `/wp/v2/history/{id}` для детали события, см. раздел «REST API» выше.
- Блок «Вятский край: семь веков истории» на главной странице (`IndexView.vue`, `useHistoryMilestones`) — тоже клиент `history/v1/events?city=kirov&per_page=1000` (один разовый запрос всех событий Кирова при загрузке главной, без пагинации): из событий каждого века выбирается случайное, год для подписи берётся из `history_date_value` (всегда чистые 4 цифры), а не из `history_date_text` (может быть «1780» или «18 декабря 1780 г.» — неоднородный формат, не годится для унифицированной подписи).
