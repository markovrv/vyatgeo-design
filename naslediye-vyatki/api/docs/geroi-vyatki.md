# Плагин «Герои Вятского края» (geroi-vyatki)

Файлы: `api/geroi-vyatki/` — `geroi-vyatki.php`, `register-hero.php`, `rest-api.php`, `js/adminMap.js`, `templates/single-hero.php`. Разработан по образцу `attraction` (см. `api/prompt-geroi-oopt-plugins.md` — исходное ТЗ) специально для SPA-фронтенда naslediye-vyatki; в отличие от `attraction`/`geopoints`, **не несёт своего Vue/SPA-бандла** — `vue/`, `template_for_yamap.php` и standalone-страница карты сознательно не создавались, каталог/карта будут реализованы во Vue-проекте.

## Назначение

Каталог Героев Советского Союза, уроженцев/связанных с Вятским краем (Великая Отечественная война). **Данные загружены** (215 записей, `Geroi.xlsx`, Лист1), но фронтенд ещё не написан — `VictoryFacesView.vue` пока работает на моке. Плагин закрывает конкретно карточку периода `wwii`/«Герои Советского Союза» в этом моке (см. `CLAUDE.md`, статус-абзац) — остальные исторические периоды VictoryFaces (Золотая Орда, Первая мировая и т.д.) этот плагин не покрывает.

## Зависимость

Нет обязательной — в отличие от `attraction`/`geopoints`, координаты в метабоксе вводятся тем же классическим Yandex Maps JS API v2.1, но `activation.php` с проверкой Yamaps не создавался: `templates/single-hero.php` не использует шорткоды `[yamap]`/`[yaplacemark]` (координаты выводятся текстом + ссылкой на Яндекс.Карты).

## Регистрируемые сущности

- **CPT `hero`** — `show_in_rest: true`, `supports: title, editor, comments, revisions, thumbnail`, архив включён, `menu_position: 16`.
- **Таксономия `hero_status`** — иерархическая (как категории), 2 термина: «Историческая» / «Современная». `show_in_rest: true`, `show_admin_column: true`.
- **Мета-поля** через `register_rest_field` (`register-hero.php:45-76`):
  - `hero_birth_date`, `hero_death_date` — строка, формат `дд.мм.гггг`; часть значений в источнике неполные (только год)
  - `hero_birth_place`, `hero_death_place` — текст
  - `hero_feat_description` — описание подвига (это же значение отдаётся в `/objects` как `summarize`)
  - `hero_awards` — перечень наград
  - `hero_profession` — профессия/деятельность в мирное время
  - `hero_coord` — строка `"lat, lng"`, как `attraction_coord`
  - **`hero_connection`** — характер связи с Вятским краем («родился», «жил», «работал» и т.п.). **Meta-поле, не таксономия** — было спроектировано как таксономия с парсингом по `,`/`.`, но отказались: реальные значения в колонке — не короткие метки, а россыпь предложений произвольной длины («Призван Мурашинским РВК Кировской области. Жил и работал в Кирове. Похоронен в Кирове.»), и любое автоматическое деление давало либо склеенные, либо разорванные посреди сокращений («пос.», «г.») факты. Хранится и отдаётся как обычный текст.
  - `hero_imgSrc` — URL override картинки для маркера карты; если пусто — фоллбэк на featured image
  - `hero_color` — HEX цвет маркера. Импорт-скрипт проставляет по `hero_status`: историческая → `#C27E3A` (ochre), современная → `#3C7A8C` (teal)

Gutenberg отключён для `hero`.

## Админ-панель

Два метабокса: «Подвиг и биография» (`hero_feat_description`, `hero_awards`, `hero_profession`, `hero_connection` — все textarea/text) и «Место и координаты» (карта Yandex, `id="hero_coord-input"`, + `hero_birth_place`/`hero_death_place`/`hero_birth_date`/`hero_death_date`/`hero_imgSrc`/`hero_color`).

## REST API

| Метод | Роут | Доступ | Назначение |
|---|---|---|---|
| GET | `/hero/v1/objects` | публичный | Все опубликованные герои, без пагинации |
| GET | `/hero/v1/objects/{id}/adjacent` | публичный | Предыдущий/следующий по возрастанию ID (таксономий, задающих группировку, нет — фильтровать не по чему) |
| GET | `/hero/v1/objects/{id}/nearby?max_distance={km}` | публичный | До 4 ближайших по координатам в радиусе `max_distance` км (гаверсинус), `max_distance` обязателен |

Пример живого ответа `GET /hero/v1/objects` (один элемент из 215):
```json
{
  "id": 23162,
  "coordinates": [60.6, 47.3],
  "title": "Алфёров Иван Прокопьевич",
  "place": "дер. Мысовская, Лузский р-н, Кировская обл.",
  "imgSrc": "https://testsite.vyatgeo.ru/wp-content/uploads/2026/08/placeholder-2-150x150.jpg",
  "color": "#C27E3A",
  "summarize": "Командир 109-го стрелкового корпуса, генерал-лейтенант. Умело организовал боевые действия корпуса в Выборгской наступательной операции (июнь 1944), осуществил прорыв трех линий обороны противника.",
  "content": "",
  "img": 23161
}
```

В отличие от `attraction` (там `summarize`/`content` всегда пустые в bulk-ответе), у `hero` **`summarize` заполнен** значением `hero_feat_description` — так и задумано контрактом (см. `api/prompt-geroi-oopt-plugins.md`, §1.4/§3.3): аннотация нужна сразу в каталоге/на карте, без дополнительного запроса. `content` всё равно всегда пустая строка — единственное по-настоящему тяжёлое поле (полный текст биографии), подтягивается отдельно через `/wp/v2/hero/{id}?_embed=1`.

`place` — место рождения (`hero_birth_place`), не место подвига. `imgSrc`/`img` у всех 215 записей сейчас указывают на один и тот же переиспользуемый тестовый плейсхолдер (см. «Импорт» ниже) — реальных фотографий героев в источнике не было ни у одной записи.

`/adjacent`, `/nearby` — тот же формат `navItem = { id, title, place, imgSrc, img }` (+ `distanceKm` у nearby), что и у `attraction`/`oopt`.

## REST-запросы на запись и очистка полей

`register_rest_field`/`save_post` в этом плагине защищены от известного класса бага (см. `CLAUDE.md`, «REST-паттерны на бэкенде»): `save_post` выходит раньше своей логики при `REST_REQUEST`, `update_callback` пишет `$value ?? ''` вместо игнорирования пустых значений — партиальный `PATCH` через REST не стирает остальные поля поста, а поле можно явно очистить, передав `''` (не `null` — `null` WP считает отсутствующим ключом и `update_callback` не вызывает вовсе). Проверено живым CRUD-тестом на testsite.vyatgeo.ru.

## Импорт (`api/import_geroi_oopt.py`)

Разовый Python-скрипт, читает `Geroi.xlsx` (Лист1, 221 именованная строка → 215 после дедупликации 6 повторов) и создаёт записи через REST **одним атомарным запросом на пост** (мета + таксономия + `featured_media` сразу) — намеренно не делает второй PATCH после создания, чтобы не зависеть от того, задеплоен ли на сервере фикс `save_post`/REST_REQUEST.

- Координаты без источника (`Кощеев Павел Григорьевич` — единственный такой в датасете) — случайная точка в границах Кирова (`58.545–58.660` / `49.520–49.750`).
- Фото нет ни у одной строки источника — один сгенерированный PIL-плейсхолдер грузится один раз и переиспользуется как `featured_media` во всех записях (и heroes, и oopt — общий с `import_oopt`).
- `has_real_text()` отсекает ~13 строк источника, где вместо текста биографии по ошибке (сдвиг при копировании ячеек) вклеено чужое ФИО — такие `content` оставлены пустыми, а не публикуют неверный текст под чужим именем.
- Запуск: `python import_geroi_oopt.py --only hero [--limit N] [--dry-run] [--no-skip-existing]`. `--dry-run` не делает **вообще никаких** сетевых запросов на запись (важно: до фикса он всё равно создавал реальные термины/медиа — см. код и комментарии в скрипте).

## Замечания для интеграции

- Строить `HeroesView.vue`/`HeroItemView.vue` и `useHeroes.js` по паттерну `useAttractions.js` — тот же контракт `/objects`, `/adjacent`, `/nearby`, тот же формат координат `[lat, lng]` → `[lng, lat]` для ymaps3.
- `hero_connection` — обычное текстовое поле, а не список терминов; на карточке/странице объекта выводить как есть, не пытаться собрать чипы/теги из него.
- `hero_status` — единственная таксономия, `«Историческая»`/`«Современная»`, приходит через `_embedded['wp:term']` на `/wp/v2/hero/{id}?_embed=1`.
