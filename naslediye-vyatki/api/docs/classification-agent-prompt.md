# Промпт для агента: автоклассификация коллекции «Этнография» по типам

Готовый, самодостаточный промпт — можно передать новому агенту/сессии как есть, без контекста этого чата.

```
Задача: написать Python-скрипт для черновой автоклассификации коллекции «Этнография»
(проект «Наследие Вятки», WordPress-плагин artifact-finder, CPT `finding`).

КОНТЕКСТ
В плагин недавно добавлена таксономия `finding_type` (иерархическая, REST-доступная,
поле в API называется `type`) с 10 терминами, но термины пока не проставлены НИ ОДНОЙ
из ~767 записей коллекции — сотрудники музея будут проставлять их вручную через
wp-admin. Ручная разметка 767 записей — большой объём труда, поэтому нужен
скрипт-помощник: он должен предложить для каждой записи наиболее вероятный тип
(с обоснованием), чтобы человек в дальнейшем быстро проверял и утверждал предложенные
варианты, а не расставлял всё с нуля. Скрипт НЕ должен ничего писать обратно в
WordPress — только скачивать данные и сохранять классификацию в локальный JSON-файл
для последующего ручного ревью.

ИСТОЧНИК ДАННЫХ
GET https://testsite.vyatgeo.ru/wp-json/findings/v1/findings/?per_page=<N>&page=<M>
— публичный, авторизация не нужна. Ответ:
{
  "findings": [ { "id", "title", "content", "excerpt", "thumbnail", "dimensions",
                  "cat_id", "functionality", "features", "additional_images",
                  "materials": [...names], "origin": [...names],
                  "creation_time": [...names], "receipt_time": [...names],
                  "type": [...names]  // сейчас почти всегда [] — ещё не размечено
                } , ... ],
  "total": <int>, "total_pages": <int>, "current_page": <int>
}
Скрипт должен пройти все страницы (число страниц читать из ответа, не хардкодить),
собрав все записи в один список. Базовый URL и per_page должны быть параметрами
(например через CLI-аргументы или .env), а не захардкожены — на случай смены домена
с testsite.vyatgeo.ru на прод.

ЦЕЛЕВЫЕ КАТЕГОРИИ (таксономия finding_type, ровно эти 10, без придумывания новых)
1. Костюм — одежда, обувь, головные уборы, пояса/кушаки, украшения костюма
2. Посуда — горшки, кринки, миски, ложки, кувшины, тарелки, крынки
3. Мебель — столы, стулья, лавки, сундуки, полки, шкафы, кровати
4. Предметы культа — иконы, кресты, обрядовые/церковные/религиозные предметы
5. Досуг — игрушки, игры, музыкальные инструменты, предметы праздников/забав
6. Торговля — весы, гири, безмены, деньги/монеты, торговый инвентарь
7. Промыслы — ремесленные инструменты и изделия (гончарные, кузнечные, плетение
   и т.п.), не подпадающие под более узкие категории 8-10
8. Прядение, ткачество, шитьё — прялки, веретена, ткацкие станки, притужальники,
   мотовила, воробы, иглы, напёрстки, нитки, пряжа
9. Сельско-хозяйственные инструменты — серпы, косы, плуги, бороны, сохи, цепы,
   вилы, грабли
10. Плотницко-столярные инструменты — топоры, рубанки, долота, пилы, стамески

МЕТОД КЛАССИФИКАЦИИ — гибрид rule-based + LLM, в два прохода на каждую запись:

1) Rule-based (первый проход, дешёвый и быстрый)
   - Составить словарь ключевых слов/стем для каждой из 10 категорий (см. подсказки
     выше — расширить самостоятельно синонимами и словоформами, текст на русском,
     учитывать регистр и падежные окончания через нестрогий поиск подстроки/стемминг).
   - Собрать текст записи: title + functionality + features + materials (join) —
     content обычно дублирует title, использовать как fallback, если остальные поля
     пустые.
   - Посчитать число совпадений ключевых слов по каждой категории → это rule_scores
     (dict category -> count). rule_label = категория с максимальным score, либо
     null, если ни одно слово не совпало или есть уверенная ничья (top-1 и top-2
     равны и > 0).
   - Сохранить, какие именно ключевые слова сработали (rule_evidence) — понадобится
     человеку при ревью.

2) LLM (второй проход — подтверждение/арбитраж, не с нуля на всё)
   - Дать модели: title, functionality, features, materials, creation_time,
     rule_label и rule_evidence с первого прохода, и полный список 10 категорий
     с определениями.
   - Попросить модель вернуть строго один label из этих 10 (или "unclear", если
     данных объективно недостаточно даже для человека) + краткое обоснование
     (1 предложение) + признак: согласна ли она с rule_label или предлагает другой.
   - Для экономии запросов — батчить записи (например по 10-20 штук в одном
     промпте) со строго структурированным JSON-выводом (или заставить модель звать
     tool/JSON-schema), не по одной записи за вызов.
   - Использовать актуальную дешёвую модель, подходящую для лёгкой классификационной
     задачи (перед вызовом API — свериться со скиллом claude-api за актуальными
     model id и ценами; на момент написания это, вероятно, модель уровня Haiku).
     API-ключ читать из переменной окружения (например ANTHROPIC_API_KEY), никогда
     не хардкодить и не логировать.

3) Итоговое поле final_label на запись:
   - Если rule_label и llm_label совпали → final_label = это значение,
     confidence = "high".
   - Если разошлись, или rule_label был null → final_label = llm_label,
     confidence = "low", needs_review = true.
   - Если llm вернула "unclear" → final_label = null, needs_review = true.

ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ
- Python 3, зависимости минимальные (requests + официальный SDK для LLM-вызовов;
  без лишних фреймворков).
- Устойчивость: retry с экспоненциальным backoff на сетевые сбои и rate-limit
  как для WP API, так и для LLM API.
- Резюмируемость: писать прогресс инкрементально (например построчный JSONL или
  промежуточный чекпоинт-файл) и при перезапуске пропускать уже обработанные id —
  767 записей и батчинг LLM могут занять время, скрипт должен переживать обрыв.
- Прогресс в stdout (например через tqdm или просто периодические print).
- CLI-параметры как минимум: --base-url, --per-page, --output, --model,
  --batch-size, --limit (для тестового прогона на небольшой выборке перед полным
  запуском).

ФОРМАТ ВЫХОДНОГО JSON (пример на одну запись)
{
  "id": 20622,
  "title": "Механическая прялка",
  "catalog_id": "...",
  "functionality": "предназначена для упрощения процесса прядения",
  "materials": ["дерево"],
  "creation_time": ["XIX в."],
  "rule_label": "Прядение, ткачество, шитьё",
  "rule_scores": {"Прядение, ткачество, шитьё": 2, "Промыслы": 1},
  "rule_evidence": ["прялка", "прядения"],
  "llm_label": "Прядение, ткачество, шитьё",
  "llm_reasoning": "Прялка — инструмент для прядения нити, прямое совпадение с категорией.",
  "final_label": "Прядение, ткачество, шитьё",
  "confidence": "high",
  "needs_review": false
}

По завершении вывести сводку в консоль: количество записей по каждой из 10
категорий + количество null/needs_review — это и есть план работы для ручного
ревью сотрудниками музея.

ЯВНО НЕ ДЕЛАТЬ
- Не писать никакие данные обратно в WordPress (ни через REST POST, ни как-либо
  иначе) — только чтение с сервера и запись в локальный JSON.
- Не придумывать новые категории сверх заданных 10 и не смешивать несколько
  категорий в одном final_label (одна запись — один label; если объект реально
  пограничный — это и есть кандидат на needs_review, а не multi-label).
```
